## Proposal recorded in Q.5 (not implemented, owner decision): production and staging must not call Ollama at the same time

**What happens today.** The cross-process "inference" lock is a row in the `locks` table of each store (`store.AcquireLock`, keyed by pid). Production runs on `data/store.sqlite`, staging on `data-staging/store.sqlite`, a review copy on its own file: three databases, three locks that never see each other. The new analysis worker, the detailed assessment queue and the preparation worker each take that lock around a model call, so inside one environment they never overlap; across environments nothing prevents it. Both environments point at the same Ollama at `127.0.0.1:11434`.

**What it costs.** Two environments analysing together share one 9B model: each call is slower, a call that waits behind the other environment can run into the provider timeout (120 s) and be counted as a failure (back-off 15 s doubling to 5 min), and the panel then says the local model is not running although it is. The worker also starts by itself at `serve` in every environment, so once this card is merged production and staging would each start working through their own ~2 300 vacancies (about 13 hours each at the measured 20 s per vacancy) and duplicate the same extractions in two databases.

**Options.**
1. **Staging is paused by default.** `quick_match.model_passes.paused: true` in `data-staging/config/runtime.yaml` (and in every review copy), switched off only for a verification session. No code. Fails open when someone forgets to switch it back, and does nothing for a preview that starts on the staging data (a `sift-preview` on port 8082 already does).
2. **One machine-wide lock.** The three call sites move to one helper that takes an advisory file lock (`flock`) under the user cache directory, named by provider host and port (for example `sifty/inference-127.0.0.1-11434.lock`). The kernel releases it when the process dies, so there is no pid check; production, staging, review copies and previews are all covered by one rule. The worker already treats "lock held elsewhere" as "wait and try again" (tested in `fitworker_test.go`), so the behaviour is in place; what is new is the lock itself and its tests. Cost: one small package; a long call in one environment delays the other, which is the point.
3. **Limit at Ollama** (`OLLAMA_NUM_PARALLEL=1`, a queue length). No code, but it is the source of the timeouts above and affects every other client of that Ollama.

**Recommendation.** Option 1 before the Q.6 run on staging (a one-line config change that I would do first), option 2 before this branch is merged, because after the merge production starts the worker on its own and nothing then depends on anyone remembering a setting. Decision: owner, in Q.6 as recorded in log.md.
