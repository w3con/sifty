## 3. Что изменилось

- Контракт сохраняет прежний Headline, уровни/Context, skills внутри опыта, строки мест/прав работы/notice/timezone, суммы/day rates, документы и факты. Стабильные идентификаторы строк предотвращают перенос скрытых данных на другую работу при удалении/переименовании. Маркеры выбранного источника отличают очищенное новое поле от ещё не перенесённого старого.
- В форме появились Display/Legal name, необязательные ответы Gender/Race/Ethnicity с самостоятельным описанием; гражданство не добавлено. Эти ответы исключены из действительных контекстов оценки и извлечения.
- Навыки: Beginner/Proficient/Expert/Not set; прежний уровень помечается как сохранённый до ручной замены. Опыт: Company/Role/месяц+год/Currently working here/Summary; нет Context и отдельных skills в интерфейсе опыта.
- Готовые Tiptap3.33.0 и React DayPicker9.14.0 поддерживают форматирование и календарный/ручной ввод. Поддерживаемый документ сохраняется вместе с серверной plain-text производной; форматирование видно после сохранения. Языки используют подписанные Pre-A1/A1–C2/Native, старое значение не угадывается.
- Оплата: валюта, налоговый режим и период заданы явно; Crypto accepted — отсутствие ограничения, equity/tokens — дополнение к базовой оплате. Нет выдуманного gross/net/FX-пересчёта. Part-time передаёт желаемые часы и диапазон; другие режимы не применяют сохранённые часы как ограничение.
- Страны/города, право работы по стране, IANA timezone и желаемое пересечение разделены. Местные справочники countries-and-timezones3.11.0/Intl не вызывают геокодер. Неоднозначные прежние строки сохранены. Work limits перенесены в Other requirements.

## 5. Спорные решения и компромиссы

Я первоначально свёл макет к полям и не закрепил визуальное соответствие. После замечания владельца приостановил продолжение; владелец явно велел продолжить поля, а дизайн-блоки вынести отдельно. Поэтому этот результат принимается как поля, не как законченный дизайн. Иконка user, заметная Add files и настоящий аватар включены в следующий предложенный план; не выдаются за сделанное.

Старые значения хранятся без переосмысления. Это увеличивает количество совместимых полей, но предотвращает тихую потерю данных и не создаёт второй редактируемый master. Готовые редакторы увеличили bundle приблизительно до890kB; сборка предупреждает о размере, отдельная оптимизация не выполнялась.

## 6. Что учесть дальше

- Обязательные продолжения для общего Profile: повторные таймауты анализа и частичный выход извлечения записаны как новые свидетельства в существующую карточку workflow. GET показывает4факта profile.pdf и6cv.pdf, из них6приняты/4предложены; много кандидатов отклонено по неверной форме/неточной цитате. Это не полное извлечение опыта/навыков. Не обходить grounding-проверки и не запускать inference без отдельного объёма.
- Возможные улучшения: следующий конкретный результат — переиспользуемые визуальные блоки, применённые к Profile; план подготовлен отдельно. Дата публикации/возраст вакансии записаны в баглист с предварительной оценкой80–150мин; реализация не запускалась.
- Прежние связанные дефекты: preview переиспользует backend build id при некоторых workers-only cold starts; fresh state directory дал согласованную генерацию, failed-state сохранён. Это не исправление harness. core.hooksPath остаётся unset; коммиты выполнялись через существующие guards per invocation, конфигурация не менялась.
- Что пошло не так и исправлено: сопоставление строк по позиции, воскрешение очищенных legacy-ограничений, потерянные переносы rich text, активный End picker после disable, переиспользованный editor другой новой строки, старый notice в read view, потеря неполного authorization и желаемых part-time часов возвращены тем же исполнителям и исправлены. Ошибка пути логов при переходе временно остановила Vite: восстановлен прежний проверенный Vite, затем выполнен контролируемый переход; данные не восстанавливались поверх live. Инцидент сохранить в локальной записи проекта.

## 7. Следующий шаг

Владелец проверяет поля на staging; координатор предлагает следующий план оформления/загрузок. Main/production не обновляются без отдельного решения. Примерно14:15–17:05Z по стенному времени (~170мин), из них~37мин ожидания владельца, то есть~133мин активной работы против150–240мин. Самооценка исполнителя «70мин» для одного исправления неверна: по меткам координатора оно заняло~11мин; в итог она не включена.
