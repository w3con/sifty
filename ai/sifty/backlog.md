# Sifty — product backlog

The open work for the Sifty product, the decisions locked so far, and a recommended sequence. Sifty is the public product built on the internal Sift engine under `app/`. This is the entry point for "what are we building next"; the product framing is in `kb/Strategy/sift-product.md`, the detailed research in `ai/research/sift-public-service-research.md`, and the delivered build is in `ai/tasks/job-search-assistant.md`. Status date: 2026-11-01.

## Decisions locked (2026-11-01)

The public repository contains only the application code; `ai/shared` and the whole knowledge base stay private.
The license is MIT.
The public repository starts from a clean `git init`, with no import of the existing history, because the current history is entangled with the private FCTO repository and risks carrying private data that was ever committed.
Commit hygiene follows the approach proven in the pilier blockchain repository: a human-edited census of forbidden forms, a single scanning engine, three git hooks installed through a relative `core.hooksPath` (pre-commit and commit-msg plus a pre-push backstop that re-scans the whole outgoing range to catch anything committed with `--no-verify`), and a manual whole-tree sweep before publishing a branch. Because Sifty is a single public repository rather than a private/public pair, the scanning engine is vendored into the repository under `scripts/leakcheck/`, the census is pruned of blockchain-specific forms, and generic secret patterns (cloud keys, personal access tokens, API keys, JSON Web Tokens) are added since the pilier set was tuned to one project.
Private candidate data — the CV and profile PDFs, remembered answers, and confirmed feedback — stays local, is loaded by a configurable path, and never enters the public repository.
The product is self-hosted now, but a hosted version run by us on Scaleway or OVH is expected later, so architectural decisions must not block it.
The internal engine keeps the name Sift; the public product is Sifty; the domain sifty.work is owned.
The product backend is Go, with browser automation isolated in a thin TypeScript worker running the official Playwright, and the React and TypeScript frontend unchanged, so the stack is Go plus TypeScript and no third language is added. The criteria were set by the owner and are specific to the code being written by an AI author: the language must be simple for the model to write and well-represented in its training; the compiler and first-party tooling must remove whole classes of error mechanically rather than by the author's discipline; and the toolchain must constrain architectural sprawl rather than leave it to review. Go meets all three. Strict TypeScript was rejected because its reliability rests on not reaching for the `any`, `as` and `ts-ignore` escape hatches and not skipping boundary validation, which is discipline an AI author will break to pass the compiler faster. Rust was rejected because it is the hardest language for the model and its strongest guarantees eliminate memory and concurrency bugs, a class this I/O-bound product does not stress. Go and Rust remain candidates only for a future targeted CPU-bound service, not for the core. The reasoning is in `ai/sifty/dev-setup-notes.md`.

## Foundation

1. Development setup / harness, model-agnostic — DECIDED, card written (`ai/tasks/sifty-dev-setup.md`), awaiting approval to execute. Adopt the minimal model-agnostic subset of the Validité harness: the card-folder convention, a small set of Python `work-*` commands with refusals inside, the executor-brief template, git hooks via a relative `core.hooksPath`, and a dispatch seam parameterized for Claude Code and opencode. It lives in the private repository per the pilier two-repository pattern. Targets Claude Code and opencode only (OpenAI, Kimi, DeepSeek); Warp dropped. The pilier leak scanner (kept in Python) and the public-repository wiring move to task 2.

2. Backend rewrite to Go and public repository split — card written (`ai/tasks/go-migration/GO-1_backend-and-public-repo/`), awaiting approval to execute. The backend is rewritten from TypeScript to Go as a self-contained application; the decoupling from the knowledge base happens here, because there is no reason to carry the kb-coupling into the new code. Port Stage 1 (collection and fit) and Stage 2 (application-answer preparation) to Go. Isolate browser automation — the Stage 2 form inspection and any dynamic-site collection — into a thin TypeScript worker running the official Playwright that the Go core calls, which keeps the official Playwright binding Go lacks; this sidecar pattern is also how the jobspy scraper is reused (see task 6). Make the application self-contained: the remembered answers and candidate feedback move from `kb/Applications/answers/` and `kb/Applications/candidate-feedback/` to a configurable local data directory; stop resolving paths from the FCTO git root; drop the `FCTO_STATE_DIR` and `FCTO-Catalogue` naming for Sifty naming; remove the dependence on the `ai/shared` submodule. Add file templates for where user answers and feedback are saved, as the local-data replacement for the current knowledge-base markdown records. Then extract the Go application into a fresh public MIT repository with the pilier-style leak-check hooks. Keep the later hosted version in mind so the split does not bake in a single-machine assumption. This is the largest task and is planned as its own card when authorized.

## Application features (these travel with the code, so order is flexible)

3. Deterministic weighted pre-filter / scorer. A weighted-sum scorer in Go with no dependency, modelled on Resume Matcher's deterministic scorer (keyword match, skills coverage, title match, section completeness, date consistency), as a free gate that drops obviously-irrelevant vacancies before the paid LLM assessment. At 30–50 thousand assessments a month this is a direct cost lever. Later it becomes the free-tier score and the basis for a weighted-versus-LLM quality comparison. Design in research sections 5 and 10.

4. Model separation in settings. Make the choice of provider for each stage — extraction, assessment, answer drafting — a first-class setting, and add cloud-provider-by-API-key to close the current loopback gap. The Vercel AI SDK considered earlier is TypeScript-only and does not fit a Go backend, so the Go path is either a single client against the OpenAI-compatible endpoint that most providers expose, or a Go multi-provider library, decided in this task. Note: opening the loopback gate is a security decision, not just a library addition, because the current isolation keeps subscription credentials out of billed API paths. Design in research sections 4 and 10.

5. career-ops design borrowings. Two-pass requirement matching (extract weighted requirements from the vacancy first, then match the candidate's evidence per requirement) and guardrail-cap scoring (a culture or dealbreaker conflict caps the score regardless of technical match) into assessment; grounding, sensitive-field confirmation, and maxlength counting into drafting. Design in research sections 6 and 10.

6. Collection tiering. With a Go core, native Go handles HTTP-based structured scraping well, while the jobspy family (the Python original and ts-jobspy the TypeScript port) covering Indeed and LinkedIn is reused by running it as a scraping worker that the Go core calls, the same sidecar pattern as the Playwright worker, rather than porting it. A later aggregator tier (JSearch or SerpApi) is added when reliability or volume demands it. Design in research sections 7 and 10.

7. Ghost-job / liveness detector. The main build work the product reframe implies, and not yet designed: the rules that turn collection-side signals — how long a posting persists, how often it is reposted, across how many boards it is duplicated, whether it reappears after being marked closed — into a per-posting liveness signal. Objective, collection-side, no inbox access. Framing in `kb/Strategy/sift-product.md`.

## Business model and open questions (decisions, not build work)

8. Tier model. Data and inference are two separate things a user may buy: paid licensed data or a free community pool, and bring-your-own-key or a unified subscription where we run the model for roughly what the user would spend on tokens. A roughly ten-dollar all-inclusive tier has margin once the pre-filter halves inference. Billing is monthly with a pause control. Pricing numbers are indicative. Design in research section 9 and `kb/Strategy/sift-product.md`.

9. Free community data pool, legal hinge. A free pool works without legal exposure only if it is genuinely peer-to-peer with no central store the company operates; a central-but-free pool still makes the company the operating infringer. True peer-to-peer is moderate technically and hard operationally. This needs a lawyer before building. Research sections 9 and 9a.

10. Blockchain tension to resolve. `kb/Strategy/sift-product.md` puts blockchain out of the core product, because the objective liveness detector replaces what a reviews layer was meant to provide. Research section 9a separately argued that a community layer (reviews, reputation, fraud and liveness signals, hash-anchored on-chain with content off-chain, about companies not individuals, moderated) would fit the pilier chain. The current decision is: out of the core. Record the tension and revisit only if an operator-proof public commons becomes an explicit, separate goal.

11. Legal review. Scraping and terms-of-service exposure, the EU database right, and GDPR all need review before any paid data tier; a non-profit or loi 1901 status does not cure copyright, database-right, or terms-of-service infringement. Research section 9a.

## Recommended sequence

Do the development setup (task 1) first, because all later work flows through it and it must also work for non-Claude models; it is a Python harness and is unaffected by the backend being Go.
Then the backend rewrite to Go and the public split (task 2), which is now the foundational engineering task: because the backend is being rewritten, new features written in TypeScript now would be thrown away, so the Go core comes before the features.
The application features (tasks 3 to 7) are written in Go on top of the rewritten core; the weighted scorer (task 3) is the most self-contained and the highest-leverage, since it directly cuts inference cost, and is the natural first new Go component.
The business-model and legal items (tasks 8 to 11) are decisions rather than build work; they gate the paid tiers, not the free self-hosted product, so they do not block the engineering.
