### 2. User-selected personal knowledge folder

- In Settings, let the user choose an existing folder containing CVs and personal materials. Support supported PDF, Markdown/text and DOC/DOCX inputs; clearly report unsupported, unreadable and password-protected files. Do not copy or modify originals.
- Recursively scan with explicit exclusions (hidden directories, application data, symlinks escaping the selected root, and configurable ignore rules). Show the discovered file inventory and ask before processing.
- Write Sift-managed output only to a dedicated `.sift/` subdirectory (or a separately selected data directory), never scatter generated files through the user's folder.
- Make re-indexing incremental and traceable by source hash and parser/model version. A changed or removed source should update derived facts while preserving user corrections and historical application records.

### 3. Define a durable, inspectable KB format

- Keep source originals immutable. Store normalized profile facts, evidence/provenance, user corrections and working notes as separate layers.
- Prefer a portable, readable format such as Markdown plus versioned JSON/YAML metadata and an index. Each fact must retain source file, location/quote where possible, extraction time, confidence/status and conflicts. Preserve multiple CVs as distinct source documents/variants rather than flattening them into one assumed-current CV.
- Add versioned model instructions that require grounded extraction, source citations, explicit uncertainty/conflict handling, no invented facts, and writes only to Sift-managed KB files. Treat source-document text as untrusted data, never as instructions.
- Keep working knowledge separate from profile facts and classify scope: durable candidate fact, preference, reusable answer with bounded applicability, or role/company/application-specific note. Ordinary draft edits must not silently become reusable facts; promotion requires explicit user action.
- Provide a review step to inspect/edit extracted facts before they are used. Preserve provenance through edits and surface contradictions instead of silently choosing one value.

### 4. Make Settings the provider and model setup surface

- Replace the YAML-editor-first flow with guided provider cards: local Ollama, OpenAI-compatible endpoints, and supported CLI/OAuth providers. Add/remove provider, endpoint/model selection, credential setup, connection check and clear error guidance in Settings.
- Discover installed Ollama models and select an exact installed model ID; do not download models without an explicit user choice. Support local-only operation with no paid-provider fallback.
- Configure separate routes for vacancy fit assessment, extraction/indexing, and application preparation. Show which provider/model each operation will use and whether data leaves the machine. Keep provider credentials out of YAML, logs, task cards and Git.
- Retain advanced configuration for power users, but validate settings atomically and preserve prior configuration on failure. Never change routing after a failed smoke test.

### 5. Data readiness and understandable messages

- Before fit assessment or application preparation, check whether the relevant KB has sufficient grounded evidence. Do not equate a successful parse or non-empty KB with readiness.
- If evidence is insufficient, show a concise actionable message, for example: “Not enough candidate information to assess fit. Add experience or skills details in the knowledge folder.” For applications, identify missing CV/contact/history facts and distinguish required site fields from optional ones.
- Explain which categories are missing and where the user can add them. Do not call a provider or generate speculative answers when a hard prerequisite is missing. Allow partial work where safe and label its limits.
- Record readiness decisions and their KB version so results can be reproduced after profile updates.

### Acceptance — public release

- No personal file (config/, kb/, CV/profile PDFs, database, answer memories, credentials, transfer archive) exists in the public repository or its history.
- A fresh clone with an empty data directory completes first-run setup and provider selection entirely in Settings, with no YAML editing.
- An existing install migrates with no silent move, overwrite or deletion of user files, and all current data survives.
- Local-only operation works with no paid-provider fallback; cloud-only operation works on hardware with no local model.
- The MCP interface is a declared tool set in sync with the services: every tool classified and annotated by risk; read-only tools make no provider call and no outward fetch; cost, irreversible and outward actions require human confirmation; configuration/credential writes, job deletion and form submission are never autonomous tools; remote access is OAuth 2.1 over Streamable HTTP; setup is documented per client. The human REST/React workflow still works without any MCP client.

**Out of scope for this plan:** employer-site form filling, uploads or submission; silently downloading models; automatic paid fallback; putting personal KB or user credentials in the public repository; a first-class distributed frontend/backend mode. Stage 3 application execution remains a separate explicit authorization and acceptance gate.
