# Application preparation behavior specification

Written from the code of main `d49de9f` on 2026-11-13 by card OPS-11; not yet reviewed by the owner.

All paths are relative to the repository root. Line numbers refer to main `d49de9f` (no code has changed since in `backend/`, `frontend/` or `config/`). Statements marked "not verified" were read from the code or from the production data but not exercised by running the application. Production counts were read with read-only queries on 2026-11-13.

## 1. Purpose

The owner shortlists a vacancy, and Sifty then does two kinds of model-assisted work for it. First it reads the employer's application form with a headless browser and lists the questions, without any model and without filling or submitting anything. Second, on request, it drafts editable answers to those questions from the owner's evidence (confirmed profile, documents, knowledge-base files, owner feedback). Separately a detailed model assessment (summary, evidence quotes, confirmed mismatches, candidate unknowns, employer unknowns) compares the vacancy text with the same evidence. The owner reviews and edits, opens the employer page, applies by hand, and then tells Sifty the outcome. Only the owner's confirmation moves a role to Applied. The deterministic Fits you and You fit scores are not described here; see [Quick Match](quick-match.md).

## 2. Terms and the three background workers

- Shortlist is the interface name of the stored stage `preselected` (the requirement map calls it Preparation). Inbox is stage `triage`, Dismissed is `no`, Applied is `applied`. `backend/internal/store/core.go:14-23`, `frontend/main.tsx:106-115`.
- Three workers run in the server process and tick once per second: the assessment worker, the preparation worker and the fit worker. `backend/cmd/sifty/serve.go:135-162`, `backend/internal/background/assessment.go:68-84`, `backend/internal/background/preparation.go:72-88`.
- The fit worker (requirement extraction and optional matching, the source of Fits you and You fit) is specified in [Quick Match section 14](quick-match.md) and is not described here.
- Every model call of the three workers runs under one machine-wide operating-system file lock that is taken without waiting, so only one model call runs at a time across all Sifty processes on the machine. A holder that finds it busy skips and tries on its next tick. The file is `sifty/model.lock` under the user cache directory unless `SIFTY_MODEL_LOCK` names another path. `backend/internal/modellock/modellock.go:28-47`, `backend/internal/dirs/dirs.go:85-100`.
- Form inspection (reading questions) never takes the model lock. `backend/internal/background/preparation.go:137-205`.

## 3. What triggers the work

- Moving a role to Shortlist from any other stage queues a model-free inspection operation (`inspect: true, generate: false`) for that role. `backend/internal/server/routes.go:163-178`.
- The same transition inserts an assessment-queue row with priority 0 (a row for that role is created or reset to pending). `backend/internal/store/jobs.go:814-822`.
- Pressing "Assess now" on the Application tab first rebuilds the derived candidate context from local files and the confirmed profile (no remote profile fetch, no model call), then inserts or resets the role's assessment-queue row with priority 100 and an optional provider override. `backend/internal/server/routes.go:273-300`, `backend/internal/profile/service.go:322-350`, `frontend/RoleContent.tsx:54,58`.
- Saving owner feedback on the Application tab writes a feedback file and also queues the role for reassessment with priority 100. `backend/internal/server/routes.go:835-872`, `frontend/RoleContent.tsx:67`.
- When the assessment queue switch is On, the assessment worker also sweeps every non-hidden role every 30 seconds and queues each role whose queue row is missing or has a different vacancy fingerprint, so the queue is not limited to shortlisted roles. A role hidden by an active stop-word is skipped. `backend/internal/background/assessment.go:125-129`, `backend/internal/store/queue.go:733-765`.
- The assessment queue switch ("Assess vacancies" in Settings, Assessment queue) is stored in `queue_state` key `config`, defaults to On when absent, and while it is Off the worker does nothing, so "Assess now" only leaves a pending row. `backend/internal/store/queue.go:238-257,276-287`, `backend/internal/background/assessment.go:116-121`, `backend/internal/server/routes.go:532-548`, `frontend/Settings.tsx:75`.
- Opening the Application tab of a shortlisted role with no saved draft revision and no earlier operation queues an inspect-and-generate operation if a preparation stage provider is configured. In practice the selection-time inspection operation already exists, so this auto-start normally does not fire. `frontend/ApplicationDraft.tsx:38,42`.
- The owner can start preparation explicitly: the primary button ("Prepare application" or "Retry preparation") sends inspect plus generate; under "More actions", "Reinspect questionnaire" sends inspect only, "Prepare unanswered fields" sends generate only, and "Regenerate this answer" sends generate for one field. `frontend/ApplicationDraft.tsx:34,70,74,77`.
- The prepare endpoint refreshes the derived candidate context first, then queues the operation. If an operation for the role is already queued or running, the existing operation is returned and the new request is dropped. The server does not check the role's stage; only the interface gates on Shortlist. `backend/internal/server/routes.go:891-911`, `backend/internal/store/application.go:173-203`, `frontend/RoleContent.tsx:69`.
- The "login" flag the interface sends ("Open owner login browser", "Sign in to continue") is ignored by the backend; no login browser is opened by the server. `frontend/ApplicationDraft.tsx:70,74`, `backend/internal/background/preparation.go:140-165` (no read of the flag).
- Nothing starts preparation or assessment for the whole catalogue. Preparation is per role and on request; the assessment sweep above is the only bulk path and only runs when the switch is On.

## 4. The queues

### 4.1 Assessment queue (one row per role)

- Order: highest priority first, then lowest role id. Only rows with status `pending` or `failed` whose retry time has passed are taken. `backend/internal/store/queue.go:574-585`.
- One role at a time, under the model lock. A role that has been deleted in the meantime is marked done without a call. `backend/internal/background/assessment.go:131-157`.
- Row states in the API are `pending`, `running`, `failed`, `done`; the count `missing-description` is reported but nothing sets it. `backend/internal/store/queue.go:289-311`.
- Running a row increments its attempt count. `backend/internal/store/queue.go:619-624`.
- A failed attempt keeps the error text and schedules a retry after 30 seconds multiplied by 2 for each earlier attempt (the doubling stops after 10 earlier attempts), never later than 6 hours. There is no attempt limit and no permanent failure state; a failing role is retried for ever on the same provider. `backend/internal/store/queue.go:635-648`.
- A failed attempt also writes a failure record to the role's assessment history and sets the role's assessment error text. `backend/internal/store/queue.go:48-81`, `backend/internal/background/assessment.go:254-260`.
- A running row whose owning process is dead is set back to pending with a 5-second delay when the worker starts. `backend/internal/store/queue.go:652-684`.
- Pressing "Assess now" or saving feedback resets the role's row to pending, replaces its fingerprint and provider, and keeps the higher priority; the row is reset even when it is currently running. `backend/internal/store/queue.go:159-188`.
- There is no cancel for the assessment queue. The only control is the switch, which stops the worker taking new rows; a running inference finishes. `frontend/Settings.tsx:75-76`.
- What the owner sees: Settings, Assessment queue shows the switch, the configured assessment and preparation models, and a table of non-done rows; the Application tab shows an assessed date or a status word (pending, running, failed, stale, assessed), the assessment error text and a stale warning. `frontend/Settings.tsx:72-85`, `frontend/RoleContent.tsx:58-62`, `frontend/filters.ts:15`. The per-role queue line and the Settings table read `job_id`, `next_at` and `elapsedMs`, while the API sends `jobId` and `nextAt` and no elapsed time, so these lines probably never match (not verified in a browser). `backend/internal/store/queue.go:142-156`.
- The per-role "Assess now" notice says "Assessment queued with priority." whether or not the switch is On. `frontend/RoleContent.tsx:54`.

### 4.2 Preparation queue (operations)

- One operation at a time across the process and across processes sharing the store: nothing is claimed while any operation is `running`. The oldest `queued` operation (lowest id) is claimed first; there is no priority. `backend/internal/background/preparation.go:246-293`.
- Statuses: `queued`, `running`, `done`, `failed`, `interrupted`, `cancelled`. `backend/internal/background/preparation.go:120-241,305-333`, `backend/internal/server/routes.go:913-930`.
- Phase one (inspect) runs first when the request asks for it. A role with no resolvable http(s) apply or original URL ends `done` with the message "no resolved application form; apply via the original listing". `backend/internal/background/preparation.go:140-155`, `backend/internal/background/inspect.go:129-151`.
- An inspection error (browser worker failure, timeout) ends the operation `failed` with the error text and the progress line "Preparation failed; saved answers preserved". There is no automatic retry; the owner retries explicitly. `backend/internal/background/preparation.go:159-171`.
- A form that was read but has no answerable fields ends `done` with a message chosen by status: sign-in required, no applicable form, backed off by the site, or "No readable questions found. Retry inspection or add questions manually.". Generation is skipped in these cases. `backend/internal/background/preparation.go:184-204`.
- After a successful inspection the operation's request is rewritten with `inspect: false`, so a retry that only waits for the model lock does not read the form again. `backend/internal/background/preparation.go:173-178`.
- Phase two (generate) needs the model lock. If the lock is busy the operation goes back to `queued` with the progress line "Waiting for shared inference slot" and is retried on the next tick, without limit. `backend/internal/background/preparation.go:217-226`.
- A generation error ends the operation `failed` with the error text; the draft is not changed. `backend/internal/background/preparation.go:228-235`.
- On start, operations left `running` by a dead process become `interrupted` with the message "Preparation interrupted; existing draft preserved. Retry explicitly." `backend/internal/background/preparation.go:305-333`.
- Cancel marks only `running` operations `cancelled`. It does not stop the browser or the model call, and does not cancel a `queued` operation. The worker's final status update is conditional on `running`, so it does not overwrite `cancelled`, but the draft write that follows an inspection or generation is not conditional, so a cancelled operation can still change the draft (not verified by running). `backend/internal/server/routes.go:913-930`, `backend/internal/background/preparation.go:166-171,229-235,465`.
- Browser discipline wraps every inspection: per-host pacing (default 5 s plus up to 3 s jitter), one browser at a time, and a per-host cooldown (default 5 min) after a site blocks the request, during which a new inspection returns the status `backed-off` without a request. The settings are `browser_interval_ms`, `browser_jitter_ms`, `browser_concurrency`, `browser_cooldown_ms` in the runtime configuration. `backend/internal/background/discipline.go:20-190`.
- What the owner sees: the Application tab polls every 1.5 seconds and shows a spinner while the form is read with no questions known, "Preparing answers…" while a generation runs, and distinct banners for sign-in required, site asked to slow down, no resolved form (link to the original listing), no questions on the form (link to apply directly), and failed, interrupted or cancelled (the error text or progress line). The button "Cancel preparation" is offered while an operation is queued or running. `frontend/ApplicationDraft.tsx:33,43-71`.
- The newest 20 operations of a role are returned with their request, progress, error and process id. `backend/internal/store/application.go:130-168`.

## 5. Which model is used

- Providers and the model chosen for each stage live in `providers.yaml` in the configuration directory (`stages.assessment`, `stages.extraction`, `stages.preparation`, and `providers.<name>` with `type`, `model`, `endpoint`, `api_key_env`, `timeout_ms`, `context_chars`). Assessment and extraction stages are required; the preparation stage is optional. `backend/internal/config/config.go:347-384,535-552`.
- Production `data/config/providers.yaml` sets all three stages to `qwen3.5-9b`, an Ollama model on `http://127.0.0.1:11434` with `context_chars: 32000`. Other configured providers are `luna` and `openai` (type `opencode`), `claude` (type `claude`, model `haiku`), `qwen3.5-4b` and `local`. The repository template `config/providers.yaml` sets all three stages to `luna`.
- Assessment: the provider is the one named on the queue row (the provider the owner picked in the Application tab, empty for automatic rows), else `stages.assessment`. A row's separate `override_provider` column is read by the worker but nothing writes it. `backend/internal/background/assessment.go:165-171,204-211`, `backend/internal/store/queue.go:159-188`.
- Preparation: the provider is `provider` in the operation request (picked under "More actions"), else `stages.preparation`; with neither, the operation fails with "no preparation provider: set stages.preparation in providers.yaml or pass a provider in the request". `backend/internal/background/preparation.go:357-362,386-388`.
- The stage provider is changed in Settings, Models, which writes the scalar into `providers.yaml` (a timestamped backup is kept in the config backup directory) and reloads the configuration; the new provider applies from the next call. `backend/internal/server/routes.go:757-802`, `backend/internal/config/save.go:39-41`.
- The list shown in the Application tab provider pickers comes from `GET /api/assessment-options` and `GET /api/stage-providers`. `backend/internal/server/routes.go:550-567,732-755`.
- There is no automatic fallback to another provider on failure. The configuration file says so, and the code has no fallback path. `config/providers.yaml:36` (comment).
- Provider adapters: `opencode` and `claude` run the command-line tool in a stripped environment with tools disabled; a tool call by the provider is refused; `ollama` and `compatible` post to a loopback endpoint only (any other host is refused). `backend/internal/assess/infer.go:51-292`.
- A request longer than the provider's `context_chars` is refused before the call. `backend/internal/assess/infer.go:51-54`.
- Prompts are embedded in the binary from `backend/internal/prompts/assessment.md` and `backend/internal/prompts/application-preparation.md`; the copies in `config/prompts/` are not read by the code (not verified beyond the absence of a reference). `backend/internal/prompts/prompts.go:7-14`.

## 6. Evidence the model receives

### 6.1 Candidate context (the shared evidence)

- Both stages draw on the latest stored candidate context. It is rebuilt from the configured sources by "Refresh" in Settings, by every profile save (local files only), and by "Assess now" and preparation requests. `backend/internal/candidate/context.go:279-506`, `backend/internal/server/routes.go:596-636`, `backend/internal/profile/service.go:300-350`.
- Sources, in this order: the files listed under `files` in `candidate.yaml` (relative to the data directory; production: `cv.pdf`, `profile.pdf`, `kb/Strategy/positioning.md`, `kb/faq.md`), the remote profiles under `profiles` (production: website, LinkedIn, GitHub, engineering practice; cached for `cache_hours`, 168 by default), owner feedback records from the feedback directory, and the confirmed profile as one source. `backend/internal/candidate/context.go:295-479`.
- The knowledge base in the current code is therefore only the markdown files named in `candidate.yaml` `files`; there is no separate answer store. Each source carries a category and scope from `source_roles` in the same file; feedback sources carry the category `owner-confirmed-feedback`. `backend/internal/candidate/context.go:464-477,157-166`.
- `review_notes` in `candidate.yaml` (unresolved conflicts the model must not resolve) are sent with every request. `backend/internal/candidate/context.go:482-496`.
- Remembered answers (files in the answers directory) are not part of the context. `backend/internal/candidate/context.go:279-506` (no read of the answers directory).
- A source with status missing has no text and contributes nothing. Production context at profile revision 42 held nine sources, all available. `backend/internal/candidate/context.go:317-322`.

### 6.2 Model assessment

- The evidence is split into paragraphs; paragraphs that share the most words with the vacancy are kept first within a budget of 78% of the space left in the provider's `context_chars`, evenly divided between sources, and numbered E1, E2, … (each paragraph cut into pieces of 650 characters). If no evidence remains the assessment fails with "no candidate evidence available". If the vacancy alone exceeds the budget it fails with "job exceeds context budget; select larger model budget (no silent truncation)". `backend/internal/assess/assess.go:141-236,288-307`.
- The request text built for the provider is the assessment prompt, the schema and the vacancy data (title, company, description, description status, location). The evidence bank and the candidate overview are not part of that text, although the prompt tells the model to choose evidence identifiers "from candidate.evidence". The retired TypeScript version sent the candidate overview and evidence bank in the same place (`legacy/app/src/providers.ts:121`). `backend/internal/assess/assess.go:308`, `backend/internal/prompts/assessment.md`.
- The schema sent is the placeholder `{"type":"object"}`, so no provider-side schema enforcement happens for Ollama, compatible or Claude. `backend/internal/assess/assess.go:294,310,413-415`.
- Production history is consistent with this: the 301 failed assessment attempts recorded up to 2026-11-05 include 68 "model output is not valid JSON … cannot unmarshal object into … RawModel" errors, 66 "unsegmentable source ai/HANDOVER.md" errors and 148 request timeouts, and the last successful assessment with a summary dates from 2026-11-05 (the assessment queue has been Off since). It was not verified that the missing evidence bank caused any of these.

### 6.3 Application answers

- Fields that are drafted: not removed, not "uncertain" in label status, not of type file, and (unless one field is requested) not edited and with an empty value. A single requested field is regenerated even if it has an answer or an edit. If no field qualifies the operation fails with "no unanswered readable questions; inspect, add questions or regenerate an individual answer". `backend/internal/prepare/prepare.go:337-360`.
- The request text is the preparation prompt, the schema (also the placeholder `{"type":"object"}`), the questions without their answer state, the language, the vacancy description marked untrusted, the candidate overview (preferences, review notes, source status) and the evidence bank, with the evidence budget capped at 45 000 characters and shrunk until the request fits `context_chars`. `backend/internal/prepare/prepare.go:362-414`.
- The evidence bank is built the same way as for assessment but without splitting paragraphs. The evidence is chosen by word overlap with the vacancy and the questions. `backend/internal/prepare/prepare.go:213-300`.
- The candidate source text is lost before it reaches `prepare.Prepare`: the worker converts the stored context through JSON into a type whose text field is excluded from JSON, so every source arrives with empty text and the evidence bank is empty (read from the code; not verified by running). `backend/internal/background/preparation.go:372-383`, `backend/internal/prepare/prepare.go:21-29`.
- The server wires no model call for preparation: the worker is created with a nil inference function, and the provider description passed to preparation carries only the model name and context size, not the provider type or endpoint. Starting a generation therefore reaches a nil function call after the prompt is built (read from the code; not verified by running). `backend/cmd/sifty/serve.go:154`, `backend/internal/background/preparation.go:390-393,420`, `backend/internal/prepare/prepare.go:182,416`.
- Production has never recorded a Go-generated draft: the application revision history holds no "Generated with" entry; the last model-drafted revision dates from 2026-10-31. The 52 drafts with questions in production come from inspection.
- The prompt rules the answers must follow: language of the questionnaire; only supplied evidence, each factual answer citing evidence identifiers; unknown answers left empty with an explanation of what the owner must establish; no invented contact details, authorisation, salary, dates, availability or consent; exact listed options for select, radio and checkbox; maximum lengths; a required cover letter is an ordinary editable field; only the existing `cv.pdf` or `profile.pdf` may be suggested and no tailored CV is generated. `backend/internal/prompts/application-preparation.md`.

## 7. The model assessment result

- A result holds a heuristic score, a summary, evidence items (claim, source, exact quote), gaps, confirmed mismatches, candidate unknowns and employer unknowns. `backend/internal/assess/assess.go:97-105`.
- Grounding is checked by code: an unknown evidence identifier fails the assessment ("unsupported evidence reference"); each evidence quote is resolved to the exact original substring or fails; each confirmed mismatch must cite a real evidence identifier and an exact quote of the vacancy requirement. `backend/internal/assess/assess.go:314-338,392-400`.
- A mismatch whose reason reads as "not mentioned / unknown" becomes a candidate unknown; a mismatch about an explicit absence stays confirmed only if its evidence comes from owner-confirmed feedback that states the absence; otherwise it is listed as "Unconfirmed: …" among candidate unknowns. `backend/internal/assess/assess.go:340-390`.
- Stored with each result: vacancy fingerprint, context version, profile id and revision, provider name, model, prompt hash and creation time. `backend/internal/background/assessment.go:263-277`.
- A stored result is marked stale when read if the vacancy, the derived context version or the confirmed profile revision differs from what was recorded; a result without those fields is stale. The interface shows a warning and keeps the old text. `backend/internal/store/jobs.go:121-160`, `frontend/RoleContent.tsx:59`.
- Each result and each failure is appended to the role's assessment history; the latest result is kept on the role. A success clears the role's assessment error. `backend/internal/store/queue.go:11-81`.
- The owner sees the summary, the Fits you number beside it, evidence with quotes, three lists (Confirmed mismatches, Unknown employer details, Candidate facts / questions) and a provenance block. `frontend/RoleContent.tsx:58-65`.

## 8. The application draft

- One draft per role: revision number, fields, selected file (`cv.pdf` or `profile.pdf`, default `profile.pdf`), the inspected questionnaire, provenance and notes. `backend/internal/store/application.go:11-47`.
- A field holds question metadata (label, instructions, type text/textarea/select/radio/checkbox/file, options, required, maximum length, language, origin site or manual, signature) and answer state (value, edited, removed, changed, unknowns, evidence quotes). `backend/internal/prepare/prepare.go:100-121,143-155`, `backend/internal/background/inspect.go:70-81`.
- Questions come from the form inspection or from the owner adding one by hand. A manual question gets origin `manual`, type default `textarea` and an empty value. `backend/internal/store/application.go:94-127`, `frontend/ApplicationDraft.tsx:78`.
- Re-inspection merges into the existing draft: answers and edits of existing questions are kept and their metadata updated; a question whose signature changed is flagged "changed" ("Question requirements changed; review your retained answer."); a site question that disappeared stays and is flagged "removed"; manual questions stay unchanged. `backend/internal/background/inspect.go:37-110`, `frontend/ApplicationDraft.tsx:9`.
- A questionnaire with no fields and a blocked, sign-in, unsupported or backed-off status keeps the existing draft and adds the note "Inspection could not read the questionnaire; existing fields and answers retained." `backend/internal/background/inspect.go:28-35`.
- Generation overwrites value, evidence and unknowns of the drafted fields and leaves the rest; if the model returns a selected file it is stored. It does not record provenance in the draft; the revision reason "Generated with <provider>" is kept only in the revision history. `backend/internal/background/preparation.go:425-466`.
- A generated answer is rejected, and the whole generation fails, if the model answers an unknown or duplicate question, cites an unknown evidence identifier, gives a list for a non-checkbox (or the reverse), invents an option, or exceeds the maximum length. An answer with a value but no evidence is emptied and given the unknown "No supporting candidate evidence; owner clarification required."; a question the model skipped is left empty with "No draft returned for this field; owner review required." `backend/internal/prepare/prepare.go:421-494`.
- There is no separate cover-letter artifact: a cover letter exists only if the form has a field for it.
- The interface shows each question with its source link, type and limits, unknowns as warnings, the evidence quotes under "Answer evidence", and "No answer yet." for an empty value. It also shows the questionnaire coverage (status, destination, language, gaps, technical record), the file selector with a preview and link to the PDF, the provenance and revision block, and a "Copy draft answers" button that copies label and value of every field to the clipboard. `frontend/ApplicationDraft.tsx:9-12,75-79`.
- The PDF endpoint serves `cv.pdf` or `profile.pdf` inline from the `evidence` folder of the data directory. Production keeps both files in the data directory root and its `evidence` folder holds only `profile-documents`, so the preview and link probably return an error there (directory listing checked; request not made). `backend/internal/server/routes.go:1178-1191`, `backend/internal/dirs/dirs.go:67`.

## 9. Editing and saving a draft

- Adding a question: `POST /api/jobs/{id}/application/questions` appends the question and saves a new revision "Manual question added". `backend/internal/server/routes.go:956-975`.
- Choosing the file: `PATCH /api/jobs/{id}/application` with `selectedFile` is saved as a new revision "user update". `backend/internal/server/routes.go:932-954`, `frontend/ApplicationDraft.tsx:79`.
- Saving an answer: the interface sends `{fieldId, revision, value}`, but the server decodes the body straight into the draft record, which has no `fieldId` or `value`; the field value is not changed, the sent `revision` replaces the draft's revision before it is incremented, and a revision is written. The documented contract in `docs/architecture/backend-api-contract.md:152` (a field edit with an optimistic revision check) is not implemented, so an owner's typed answer does not persist (read from the code; not verified in a browser). `backend/internal/server/routes.go:945-949`.
- Every write of the draft (inspection, generation, question, edit) increments the revision and appends the full draft to the revision history table, which is never trimmed. `backend/internal/store/application.go:50-91`.
- Unsaved edits stay in the browser while switching tabs; the "Save answer" button saves one field and "Regenerate this answer" is disabled while the field has unsaved changes. `frontend/ApplicationDraft.tsx:6,13`.
- There is no revision check on a write: a generation loads the draft, waits for the model, and writes back the whole draft, so it can overwrite changes made meanwhile (card APP-7). `backend/internal/background/preparation.go:395-465`.
- Closing the browser tab, restarting the server or cancelling never discards the saved draft.

## 10. Remembering answers

- Under each non-file field the owner chooses a scope (this role only, this company, general candidate fact) and presses "Remember for future applications". The interface sends `{fieldId, revision, scope, confirmed: true}` to `POST /api/jobs/{id}/application/remember`. `frontend/ApplicationDraft.tsx:14,77`.
- The server decodes that body as a complete answer record and writes it without filling in the id, creation time, question or answer text from the draft. A body without a creation time makes the file name step fail (index out of range) and the request returns an error (read from the code; not verified by running). `backend/internal/server/routes.go:977-996`, `backend/internal/records/records.go:131-134`.
- When it works, one markdown file per answer is written into the `answers` folder of the data directory, named `<date>-<id>.md`, created with exclusive create (an existing file is never overwritten), holding the verbatim question and answer, scope, company, role id, draft and field revision, and an embedded base64 record. `backend/internal/records/records.go:117-161`, `backend/internal/records/templates/answer.md.tmpl`.
- `GET /api/jobs/{id}/application/memories` lists the remembered answers recorded for this role only; the interface does not call it. `backend/internal/server/routes.go:998-1022`.
- Remembered answers are not read by preparation or assessment (card APP-6). The production `answers` folder is empty.

## 11. Applying by hand and recording the outcome

- "Apply" (key A) exists only in the Shortlist view for a shortlisted role. It opens the employer apply link, or the original listing if none is resolved, in a new tab and then opens the confirmation dialog. If no valid http(s) link exists or the browser blocks the tab, an error is shown and the role stays in Shortlist. `frontend/main.tsx:106-115`.
- Sifty never fills or submits a form: the browser worker blocks every request except GET, HEAD and data-loading POSTs to paths containing `/api/`, `/graphql` or `/query/`. It does click an "Apply" control to reach the form. `backend/workers/playwright/index.mjs:150-200,228-245`.
- The dialog "Did you submit your application?" offers five buttons: "Not yet" (closes, nothing changes), "No, vacancy is stale", "No, vacancy is closed", "No, not suitable" (each moves the role to Dismissed with that stored reason) and "Yes, applied". It closes only through a button, never by Escape or an outside click, and a failed save keeps it open with the previous state. `frontend/ApplicationConfirmation.tsx:20-103`.
- "Confirm application…" in the Shortlist view opens the same dialog later. `frontend/main.tsx:166`.
- Applied is accepted only for a role in Shortlist with `confirmed: true`; it stores the applied time and a workflow history row. A negative outcome is accepted only for a role still in Shortlist, stores the reason and a history row, and sets no applied time. `backend/internal/store/jobs.go:741-812`.
- Applied roles are listed under Applied and are removed permanently after 30 days from the applied time by a method that no scheduler calls yet (documented in `docs/MAP.md`, card GO-7). `frontend/main.tsx:168`, `backend/internal/store/jobs.go:1087-1114`.

## 12. What is written to disk

- SQLite store (`store.sqlite` in the data directory): `application_drafts` (current draft), `application_revisions` (every draft write with its reason), `preparation_operations` (every operation with request, progress, error), `questionnaire_snapshots` (each inspected form), `assessments` (every result and failure), `assessment_queue`, `queue_state` (the switch), `context_refreshes` and `contexts` (candidate context snapshots), `workflow_history`, `feedback` (index). The role row carries the latest assessment and assessment error. `backend/internal/store/migrate.go:69-200`.
- Files in the data directory: `answers/<date>-<id>.md` (remembered answers), `feedback/<date>-<uuid>.md` (owner feedback with extracted facts and conflicts, written with exclusive create and indexed in the database afterwards), and a timestamped backup of `providers.yaml` under the configuration backup directory on a stage change. `backend/internal/records/records.go:117-220`, `backend/internal/server/routes.go:857-863`, `backend/internal/config/save.go:39-41`.
- Read only: `cv.pdf` and `profile.pdf` (served; also read as context sources), `kb/` files and the `candidate.yaml` sources.
- Outside the data directory: only the model lock file (section 2).
- Nothing is written for an application that was only opened; submission is recorded solely by the owner's confirmation (section 11).

## 13. What leaves the machine

- Form inspection: a headless browser on this machine requests the employer's application page (and the data requests the form makes). No profile or answer data is sent; non-data POST requests are blocked. `backend/workers/playwright/index.mjs:228-245`.
- Model assessment: the assessment prompt and the vacancy (title, company, location, description). With the placeholder behaviour in section 6.2 no candidate text is in the request; if the evidence bank is added later, the selected candidate paragraphs and preferences would be sent as well. The request goes to the configured provider: a local Ollama or compatible server on loopback (nothing leaves the machine), or the `opencode` or `claude` command-line tool, which send the request to their hosted service under the owner's own subscription login. `backend/internal/assess/assess.go:288-310`, `backend/internal/assess/infer.go:106-181,195-197`.
- Application drafting (when a model call exists): the preparation prompt, the questions, the vacancy description, the candidate overview and the selected evidence paragraphs (CV, profile, knowledge-base files, feedback, confirmed profile) to the configured provider as above. `backend/internal/prepare/prepare.go:396-397`.
- Production stages point at the local Ollama model, so by default none of the above leaves the machine; choosing `luna`, `openai` or `claude` for a call sends it to a hosted provider. There is no per-call warning or cost display for the assessment or preparation stages (the paid-provider guard in [Quick Match section 14.7](quick-match.md) covers the fit worker only). `data/config/providers.yaml`.
- Remote profiles in `candidate.yaml` are fetched over the network only when the owner presses a context refresh with remote refresh, never by a profile save, "Assess now" or preparation. `backend/internal/candidate/context.go:342-368`, `backend/internal/profile/service.go:322-350`.

## Known limits and defects

- Application drafting has no working model path: no inference function is wired, the provider description lacks type and endpoint, and candidate source text is dropped before the evidence bank is built (section 6.3). No card.
- Both prompts are sent with the placeholder schema `{"type":"object"}`, so providers do not enforce the answer structure (sections 6.2, 6.3). No card.
- The assessment request omits the evidence bank and candidate overview that the prompt tells the model to cite (section 6.2). No card.
- Saving an edited answer does not persist the value (section 9). No card; [APP-7](../../work/tasks/application-preparation/APP-7_draft-revision-check/description.md) assumes it works.
- "Remember for future applications" cannot complete as the interface calls it (section 10). No card.
- "Assess now" does nothing while the assessment switch is Off, which is the production state (2107 pending rows, switch Off), and the notice still says it was queued. No card.
- The assessment queue is not limited to shortlisted roles when the switch is On, and failed rows retry for ever with no attempt limit (section 4.1). Partly [INBOX-1](../../work/tasks/inbox/INBOX-1_search-catalogue-overview-quick-match/plan.md) step 3.2.
- Queue status in the Application tab and Settings reads fields the API does not send (section 4.1). No card.
- Fingerprints written by "Assess now" and by feedback use a shorter vacancy hash than the sweep and the shortlist transition use; the next sweep can therefore replace the fingerprint and set the finished row pending again, assessing the role a second time (read from the code; not verified by running). `backend/internal/server/routes.go:1235-1243`, `backend/internal/store/core.go:130-150`. No card.
- Cancel does not stop the work or a queued operation, and the draft can still change afterwards (section 4.2). No card.
- Role stage is not checked on the server for preparation; only the interface prevents preparing a role outside Shortlist. No card.
- The "Open owner login browser" and "Sign in to continue" actions send a flag the server ignores; there is no login flow in the application (the Settings text points to a command in the retired TypeScript README). No card.
- The PDF file endpoint and the production file layout disagree (section 8). No card.
- The queue state has a `paused` flag that nothing sets and the worker does not read; a `runtime` row is read by the API but nothing writes it. No card.
- The assessment panel shows provenance fields (selection, mismatch evidence, input fingerprint) that the stored result does not contain. No card (not verified in a browser).

## Contradictions

- `docs/MAP.md` R-ASM says moving a role to Preparation or pressing "Assess now" runs the assessment. The code also assesses every non-hidden role through the 30-second sweep while the switch is On, and does nothing at all while it is Off; the comment at `backend/internal/store/jobs.go:814-815` says shortlisting is the only automatic enqueue point, and the sweep is in `backend/internal/background/assessment.go:125-129`. The owner's words in INBOX-1 say the detailed assessment is for shortlisted roles.
- `docs/MAP.md` R-APP lists "draft editing and remembering" as implemented. The save-answer and remember calls are not served as the interface sends them (sections 9, 10).
- `docs/MAP.md` R-APP says the form-inspection worker crashes on startup (`worker inspectForm: exit status 1`) and that preparation is not working end to end. Production data shows inspections finishing `done` through 2026-11-13 and the failures with that error ending on 2026-11-04 (stale worktree paths in their messages); the end-to-end gap is instead in generation (section 6.3). Whether the inspection crash can recur on a fresh build was not verified.
- `docs/MAP.md` R-APP says drafts are made "from candidate evidence" and "Known partial parity" lists only remembered answers and the revision check. The code has no model call for drafting and drops the evidence text (section 6.3).
- `docs/architecture/backend-api-contract.md:149-154` says prepare defaults to provider "openai", requires a pre-selected role and that the PATCH field edit checks the revision; the code defaults to `stages.preparation`, does not check the stage and has no field-edit branch.
- `docs/architecture/backend-api-contract.md:154` says memories are "applicable to the role"; the code returns only records saved from this role.
- `backend/internal/prepare/prepare.go:8-9` says remembered answers are bound into the context by the store; no code does this ([APP-6](../../work/tasks/application-preparation/APP-6_answer-memories-in-prepare/description.md) says the same).
- [APP-6](../../work/tasks/application-preparation/APP-6_answer-memories-in-prepare/description.md) says the remember and memories routes "already work" and must not be touched; the remember route does not complete as called (section 10).
- [APP-7](../../work/tasks/application-preparation/APP-7_draft-revision-check/description.md) says "on a matching revision apply the edit as today"; the edit is not applied today (section 9).
- [ASM-1](../../work/tasks/assessment/ASM-1_rerun-failed-with-model/description.md) says a per-retry provider override already exists on the row; the worker reads it but no route or store method writes it, and the failed rows retry on the same provider.
- The interface calls the stage Shortlist while `docs/MAP.md`, the owner's words and the decision record call it Preparation; both name stage `preselected`.
