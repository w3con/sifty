Durable capture of two investigations run on 2026-11-01: how the Validité application organizes development work, and how the pilier blockchain repository keeps its public git history clean. ## Validité harness — the two-layer design

The Validité application runs a home-grown work-management system that is deliberately split into two layers, and it already runs from three different fronts (Claude Code, Codex, and Warp). The lower layer is plain Python, Git, and Markdown that any tool can run; the upper layer is a thin Claude Code binding. The model-agnostic/Claude split is explicit in the files themselves, which is exactly why it is worth borrowing for a product that must also be built by non-Claude agents.

A unit of work is a card, which is a folder, not a file: `work/tasks/<epic>/<ID>_<slug>/` holding `description.md` (why the work exists, owner-authored), `plan.md` (steps grouped into phases plus acceptance criteria, coordinator-authored), `log.md` (closed steps with verbatim check output, executor-authored), `comments.md`, and `attention.md`, with conditional `done.md` / `rejected.md` / `cancelled.md` / `question.md` / `trace.md`. A short card carries only `description.md` plus `comments.md` and keeps its steps and criteria inside the description. Because the card is a folder of markdown, it survives any session dying and any tool.

Each phase is its own `bin/work-*` command, and the refusal logic lives inside the scripts, so the refusals hold no matter which agent calls them. The core commands: `work-new` (allocate the next ID, write the empty file set, commit the founded folder), `work-plan` (validate the card is fit to review), `work-handover` (the gate between a finished plan and the executor: it checks its refusals, cuts a linked git worktree on a `work/<id>` branch, and prints the executor brief), `work-note` and `work-commit` (the executor records each step with verbatim check output and commits to its own branch), `work-resume` (restart a cut-short run from the last handoff), and `work-accept` / `work-finish` (run the checks in a scratch copy, fast-forward-merge the branch, write `done.md`, push, clean up). The executor's entire standing behaviour is tool-neutral text in `bin/templates/executor-brief.md`: work only in the worktree, run the narrow check per step, record then commit then move on, hand off on every stop, one full build at the end, never merge or push or raise agents.

The one design decision that makes the whole thing cross-tool is a seam: inside a live session the phase commands print the agent prompt and return a "handed to the session" exit code so the session raises the agent itself, and only when run headless do they dispatch a model on their own. The headless dispatch command is parameterized (a `WORK_*_CMD` environment seam) rather than hardwired to `claude -p`, which is what lets Warp raise agents through its own mechanism and would let opencode do the same. There is a `WARP.md` in the repository that maps the same card lifecycle onto Warp's agent runner, which proves the design is genuinely portable.

`CLAUDE.md` and `AGENTS.md` are hand-maintained twins, not generated from each other. Both open by importing a shared `rules.md` (the single source of truth for the mechanism) and then add one header line naming the audience — Claude Code for one, Codex for the other. `AGENTS.md` is the de-facto cross-tool convention file, because it is the filename Codex and opencode look for.

What is Claude-Code-only and must not be relied on for a cross-tool workflow: the global PreToolUse hooks (the spawn-sanction gate, one-card-per-conversation, pace ceilings) that live in the user's `~/.claude` and fire only inside Claude Code; the Agent/subagent tool and its agent definitions; the `claude -p` default headless dispatch; the `.claude/` skills, settings, and slash commands; and the `@rules.md` import directive, which only Claude Code auto-expands — a non-Claude tool reads `AGENTS.md` but will not expand an `@`-import, so the real rules must be inline, not hidden behind the import.

## The model-agnostic subset worth copying

The card-folder convention (`description.md` / `plan.md` / `log.md` / `comments.md` / `attention.md` plus the conditional files). A small set of work commands with the refusals inside them: `work-new`, `work-plan`, `work-handover` (print the brief, cut the worktree and branch), `work-note` and `work-commit`, `work-resume`, `work-accept` / `work-finish`. The executor-brief template as tool-neutral markdown. Git hooks through a relative `core.hooksPath` plus a machine-setup script to wire a fresh clone, and a CI workflow that calls the same single test script. `AGENTS.md` as the primary convention file with the real rules inline, and, if a `CLAUDE.md` is kept, making it a thin twin pointing at the same rules. And the cross-tool seam: scripts print the prompt and return a handed-to-session code when a live session is present, with the headless dispatch command parameterized rather than hardwired.

What to leave out so no agent is locked out: the global PreToolUse gate scripts, the `.claude/` skills and settings, the Claude slash commands, and any hardcoded `claude -p`.

## pilier — keeping a public repository's history clean

There is no history rewrite, no filter-repo, no squash-on-publish, and the CI does not scan for secrets. The clean history is achieved by preventing private data from ever entering the public repository and starting the public repository from a clean state. The original dirty history was cleaned once, by hand.

Four layers do the work. First, a private/public two-repo split: the private repository holds all internal reasoning (the `ai/` directory, the Obsidian vault, decision logs, the hook scripts), and the public repository is code only, with a `.gitignore` that hard-excludes the private directories. Second, a human-edited census of forbidden forms (a markdown file with fenced lists) plus a single scanning engine that reads the census and scans text; the census splits forms into irreversible ones rejected in every repository (private keys, mnemonics, environment-file contents, internal host strings) and untidy ones rejected only in public repositories (internal identifiers, private-repo names, tool-authorship trailers, absolute local paths). The engine is careful enough to pass a published cryptographic hash while catching a real key, and to match a mnemonic against the actual BIP-39 wordlist rather than word shape. Third, three git hooks installed through a relative `core.hooksPath`: pre-commit and commit-msg scan what is being committed, and pre-push re-scans the entire outgoing range as a backstop against anything committed with `--no-verify`. Fourth, a manual whole-tree sweep run by hand before publishing a branch, which is the only check that sees forms already sitting in the tree.

For a single public repository rather than a private/public pair, the recipe is: vendor the scanning engine into the repository under `scripts/leakcheck/` and repoint its relative paths; write a census with the three fenced lists, listing the repository's own origin so the public-only rules activate, pruning the blockchain-specific forms and adding generic secret patterns (cloud keys, personal access tokens, API keys, JSON Web Tokens); install thin in-repository hooks under `.githooks/` and set `core.hooksPath` to them, with a setup step every clone runs because the hooks path is local config and is not cloned; write a `.gitignore` from day one; and start the public repository with a fresh `git init` and a single `tree-check` before the first push, so no history rewrite is ever needed.

The pilier repository's own license is Apache-2.0, not MIT; nothing in the cleaning mechanism depends on the license.

## Decisions settled (2026-11-01)

Target tools: Claude Code and opencode only, opencode wired to OpenAI, Kimi, or DeepSeek models. Warp support is dropped. All three non-Claude models in use are stronger than Sonnet 4.6, so language fluency is not a selection factor.

Harness language: Python, lifting the proven Validité `work-*` scripts almost directly. The owner is indifferent to the harness language, so there is no reason to pay for a rewrite into another language; the pilier leak scanner is already Python too. The harness language is deliberately decoupled from the product's backend language, because a git hook invokes an executable regardless of what wrote it.

Scope: the minimal subset, without the knowledge-base traceability machinery (requirement-to-feature-to-test chains, registry and product-trace builders) that Sifty does not need yet.

Location: the pilier two-repository pattern — the cards, the harness scripts, and the leak-check live in the private repository and point at the public one.

Sequencing: the work-* harness is built in the private repository first, to manage Sifty cards now. The pilier leak scanner and the public-repository wiring are deferred to the repository-split work (backlog task 2), because no public repository exists yet to protect. The dev-setup card is `work/tasks/sifty-dev-setup.md`.

## Decision settled — the product backend language (2026-11-01)

The product backend is Go, with browser automation isolated in a thin TypeScript worker running the official Playwright, and the React and TypeScript frontend unchanged, so the stack is Go plus TypeScript with no third language. The criteria were set by the owner and are specific to the code being written by an AI author: the language must be simple for the model to write and well-represented in its training; the compiler and first-party tooling must remove whole classes of error mechanically rather than by the author's discipline; and the toolchain must constrain architectural sprawl rather than leave it to review.

Go meets all three. It is the simplest mainstream compiled language and models write it well, with a large training corpus and one idiomatic way to do most things. Its compiler rejects unused variables and imports, and go vet, go test -race, coverage and gofmt, plus the staticcheck, errcheck and nilaway linters in continuous integration, catch the error classes this product actually has: a forgotten error check, a nil dereference. Its deliberate minimalism, with no inheritance and few features, leaves the model little room to over-abstract, and gocyclo plus depguard or go-arch-lint mechanically limit complexity and enforce layer boundaries in the same integration gate.

Strict TypeScript was rejected on the owner's own objection: its reliability rests on not reaching for the any, as and ts-ignore escape hatches and not skipping boundary validation, which is discipline, and an AI author will break discipline to get past the compiler faster. Converting that into continuous-integration gates is possible but is more bolted-on scaffolding to approximate what Go gives natively, and still does not constrain architectural sprawl.

Rust was rejected because it fails the first criterion. It is the hardest language for the model and has the least forgiving compiler, so more iterations are spent on lifetimes and borrows, and its strongest guarantees eliminate memory and concurrency bugs, a class this I/O-bound product that mostly waits on the network does not stress. Its marginal reliability gain over Go-with-linters for this workload does not pay for its authoring cost.

The cost accepted: the verified Stage 1 and Stage 2 backend is rewritten in Go, and the official Playwright binding that Go lacks is kept by isolating browser automation in the TypeScript worker. The rewrite is justified by the volume of code still ahead — the scorer, the liveness detector, the collection tiers, the hosted service — relative to the two built stages. Go and Rust remain candidates only for a future targeted CPU-bound service, not for the core.
