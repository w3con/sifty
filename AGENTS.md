# AGENTS.md — work-management harness

This file is the source of truth for how work is managed in this repository. OpenCode is the primary agent tool. Keep the core workflow tool-neutral; do not add Claude Code compatibility work. The `bin/work-*` commands implement the current lifecycle, but not every behavioral rule below is enforced by code.

Roles: the owner states why a card exists; the coordinator plans it and accepts the result; the executor builds it.

The main session does only task-card planning and acceptance. Delegate all implementation and mechanical execution to subagents, including small fixes, application/tool code, configuration, ordinary documentation, file moves, builds, permitted test execution, Git operations and deployment commands. No "quick fix" or convenience exception authorizes direct implementation by the coordinator. The coordinator may read code/diffs and inspect evidence or the running app for planning/acceptance, and directly maintain task plans, acceptance records and owner-requested standing instructions. Return implementation corrections to the executor. Use the configured OpenCode Go / DeepSeek executor; do not substitute the coordinator's model or a directly billed API.

## Start or resume a session

Read [the workflow](work/WORKFLOW.md), then [the roadmap's current planning work](work/ROADMAP.md), then [the current requirement-to-code map](docs/MAP.md), then the active card's description, plan, attention and log. Inspect `git status`, the relevant diff and `git worktree list` before editing. Preserve existing changes and unrelated working copies.

Use the card's recorded approval, completed checks and next step to resume. An open checkbox or a prepared plan is not authorization to execute. Record decisions and the next action on disk before a restart or context reset; chat history is not the checkpoint.

The roadmap records the current resume point. The foundation plan distinguishes agreed direction from proposed implementation; do not treat target directories or planned automation as already available.

## Incoming requests and preparation

Maintain persistent product behavior specifications under `docs/specs/`, indexed from `docs/MAP.md`; epics and task cards link to them rather than duplicate them. Before planning a feature change, read its specification and identify the proposed change. After owner agreement, update the agreed behavior while distinguishing proposed numerical policy, implemented behavior and released behavior. At acceptance, reconcile the implementation and remaining limitations with the specification. Task cards retain the change plan, estimates, checkpoints and evidence; a specification is not a second execution plan and does not authorize implementation by itself.

Capture new bugs and ideas in the backlog without starting them or interrupting the active task. Use `bin/work-capture` to create a minimal canonical backlog card with the owner's exact wording (outer whitespace, newlines and original CR/LF included), or `--update <id>` to append evidence to an explicitly matched card. Markdown-looking text inside the captured fence is data, not metadata or steps. It never dispatches an executor, cuts a worktree, starts work or touches staging. Add evidence to an existing matching card rather than duplicating it. An explicit instruction to change the active task is steering, not merely a backlog report.

Keep one canonical card per task. Backlog and bug lists are views derived by `bin/work-list` from canonical cards; `work/backlog.md` is historical product material, not the current view. The roadmap holds sequencing and dependencies; epics describe product outcomes. During preparation and before completion, check the affected requirement in `docs/MAP.md`, the implementation, tests and dependent cards, and update the map/task index when a card is founded, cancelled, re-scoped or closed. `bin/map-check` validates the active navigation; archived historical prose keeps its old paths. Raise contradictions or scope growth before implementation and obtain approval of the complete plan.

## Coordination and implementation

### Separate data, logic and presentation

Every implementation brief must explicitly require separation of persisted/domain data and configuration, application logic/effects, and presentation. State the authoritative source of inputs and settings, where logic belongs and which components render it. Reuse existing configuration, path-resolution and provider adapters; do not embed user/profile/mockup data, machine-specific paths, environment addresses/ports, provider/model choices or adjustable limits/weights inside application logic or views. Obtain them through the appropriate configuration, parameters, data store or existing path resolver. Configurable defaults belong in one explicit configuration location, not duplicated magic values. Do not create a new settings framework solely to satisfy this rule. Coordinator acceptance checks these boundaries and actual data/configuration sources, not just build success; return violations to the same executor.

### Keep main history at card granularity

Executors may make intermediate checkpoint commits on their work branches for recovery. A successfully completed card must enter `main` as one meaningful squash commit using a Conventional Commits subject that identifies the card. Do not transfer the sequence of planning, verification, correction and handback commits into main individually. Preserve checkpoint history and recovery material until acceptance/release succeeds. The coordinator decides acceptance and the approved integration scope; delegate the Git/deployment mechanics to an explicitly assigned executor. Executors never integrate or release on their own initiative.

Foundation step 6.3 implements this policy: `work-finish` prepares one Conventional Commits squash commit whose tree is the checked source plus the generated `done.md`, releases the pinned source through the configured `WORK_RELEASE_CMD`, and only then publishes that commit on the base branch. The checkpoint branch is replaced by a `refs/work-recovery/<id>` ref after a verified successful publish. Preserve the existing readiness, revision and data-preservation safeguards; `--force` never bypasses approval, release or preservation checks. Rewriting existing history is separate work, not an automatic consequence of this policy.

### Estimate every task before approval

Every new card, including a lightweight backlog report, must record a preliminary complexity and AI development-time estimate. Refine it when preparing the plan and show it to the owner before execution. Use a short estimate block in the card, not a separate planning document:

- **Complexity:** one Fibonacci value (`1, 2, 3, 5, 8, 13, 21, …`), with a brief reason covering affected areas, coupling and uncertainty. Points are relative complexity, not a count of steps or a conversion to hours.
- **AI preparation:** approximate time for understanding, task formulation and the plan.
- **AI implementation:** approximate time for the coding subagent, including context loading, required builds and expected corrections.
- **AI acceptance:** approximate coordinator time for code review, running-app review and expected correction/review cycles under the current test policy.
- **Total AI elapsed time:** a realistic range for those phases combined, with the main assumptions and uncertainty. Exclude waiting for owner replies and identify external/tool delays separately. Do not estimate only typing time or substitute human-development estimates.

Before execution, show the owner the complete list of planned steps. For each step, state its concrete result, why it is necessary for the requested outcome, and its estimated AI elapsed time and any known monetary/external costs. Mark optional steps explicitly and show the total alongside the per-step estimates, accounting for shared preparation and acceptance without double-counting. If a monetary cost is unknown, say so rather than inventing a price. Keep this breakdown in the card and present it to the owner before work starts; an overall estimate or a bare checklist does not replace it. Added or materially expanded steps require the same explanation and revised cost before execution.

Even an uncertain incoming report gets an explicitly provisional score and time range. Separate independent outcomes when their combined estimate hides the size of the work; for scores of 8 or more, explain why the work should remain one task or propose a split before approval. Re-estimate and show the difference before expanding approved scope. At completion, record actual or explicitly approximate elapsed time and the main reason for a material overrun, so later estimates can be calibrated. The existing plan `estimate:`/`WORK_ESTIMATE_CEILING` mechanism is separate and does not satisfy this rule. This is an instruction to the coordinator; current commands do not enforce these estimate fields automatically.

### Establish actual usefulness before implementation

- Before approval, state in the card and a short owner-facing summary: the observable outcome, its actual beneficiary, the concrete action in which it will be used, how that use will be demonstrated within this task, excluded work, and the complete AI time estimate. Do not bury scope or cost inside a long plan.
- Internal tools, documentation and workflow automation require a concrete adoption path within the same approved task. Code, documents and passing tests alone do not demonstrate usefulness. If value depends on a later task to integrate, maintain or start using the result, defer the proposal instead of implementing speculative infrastructure.
- **The owner controls the development process.** Do not independently change or expand workflows, harness tools, agent instructions, hooks, planning/verification machinery or reporting requirements. Always bring discovered process problems and improvement proposals to the owner for joint consideration. Reporting them is required; implementing them requires an explicitly owner-approved process task, even when a process defect obstructs the current task.
- **Product fixes and process changes have different authority.** Independently fix product defects within the approved task's scope. Do not use that autonomy to repair or improve the development process.
- **Proportion effort to the product outcome.** Account for the full cost of delivery, including coordination, verification, documentation and commit management. Additional effort is justified for architectural quality within the approved scope: separation of data, logic and presentation, appropriate configuration and clear responsibilities. Make architectural improvements explicit: state what change is proposed, which concrete product or maintenance problem it solves, and its expected additional effort. Include planned improvements in the task plan and explain architectural decisions made during implementation in the final report. Do not present architectural scope expansion as a routine implementation detail. Do not spend additional time refining the development process or its artifacts. Keep plans, handoffs, reports and commit history clear and useful without pursuing procedural completeness.
- Treat the upper elapsed-time estimate as a stop boundary. Check elapsed time at executor handbacks and before another stage or broad investigation. If the bound is reached, preserve the work and report actual progress, remaining work and the revised estimate before continuing. An overrun is not permission for another unannounced correction/check cycle.
- Completion evidence must show the promised real use, not only completed plan steps or tool self-tests. If that evidence is absent, state that the benefit remains unproven; do not call the tool adopted or the outcome delivered.

These are behavioral approval and stopping rules, not an implemented runtime lock or timer. Do not claim technical enforcement that the commands do not provide.

The main session prepares tasks and plans, analyzes dependencies, reviews code and performs technical acceptance. The owner approves product scope and final completion. Delegate coding to the project `executor` subagent, configured in `.opencode/agents/executor.md` with model `opencode-go/deepseek-v4.1-flash`, using the owner's OpenCode Go subscription.

Launch the executor through the live session's visible subagent tool with the approved card and its worktree brief. Do not substitute another model/provider or run a hidden agent through a shell wrapper. Verify the actual executor model from session metadata rather than its self-report. If the configured agent is unavailable or the model cannot run, report the blocker without silently falling back to the coordinator's model or a direct billed API.

The coordinator maintains task plans and acceptance records directly; standing instructions are updated directly when the owner requests it. Other documentation/configuration work is delegated like code. This role split does not authorize implementation before the task's plan is approved. Provider/model profiles are replaceable adapters; the core work commands remain tool-neutral.

Assign one bounded, independently checkable stage per executor session. Its brief must name the card, worktree, exact step IDs, checks and stopping point. Listing every open step does not assign every step. Review the diff and check evidence before assigning the next stage; send corrections to the same executor while its context remains useful. Start the next independent stage with a fresh executor context in the same worktree, only after the previous executor has stopped.

The owner permits planning two or three agents when independent work shortens delivery without increasing expected total token consumption. Compare the proposed allocation with sequential execution, including repeated context, coordination, review and integration; incidental parallel-coordination overhead should stay within approximately 1–2% and be offset by savings elsewhere. Do not claim that this bound is guaranteed or measured without evidence. When the token-neutral case cannot be justified, use one executor. This permission does not authorize new orchestration infrastructure or concurrent writers in the same worktree.

One live coordinator owns a card's worktree. Record that session in the card's attention file and check ownership before writing or dispatching. A second session must not resume the same executor or edit the same worktree while that coordinator is active. A cancelled tool invocation does not prove the underlying session stopped; verify session completion before starting another writer.

If context becomes too large, save completed work, check results, unresolved findings and the precise next action in the card before handing off to a fresh executor. Distinguish current context size from cumulative token spend. Do not claim a numerical context limit or automatic enforcement unless configured and verified. The owner reviews the completed result on the card's preview server, not every technical stage.

## A card is a folder

A unit of work is a card: a folder `work/tasks/<epic>/<ID>_<slug>/`. The file set, state metadata and short/capture variants are defined in `bin/templates/convention.md`. Steps are `- [ ]` (open) or `- [x]` (closed) lines in `plan.md`, or in `description.md` for a short card. The card is markdown, so it survives any session or tool dying.

The only normal states are `backlog`, `in progress`, `review` and `done`. `description.md` carries `**Status:**`, an optional `**Kind:**` and an optional `**Blocker:**` reason; an outcome file (`done.md`, `rejected.md`, `cancelled.md`) is authoritative over stale status text or unchecked template residue. `question.md` blocks a nonterminal card; it is not a terminal outcome. Duplicate IDs and contradictory metadata are refused. Read one card with `work-status`, derived views with `work-list`; read-only navigation uses an active worktree's nonterminal state and exact next step while showing the base state separately; base cancellation, blockers or attention override the worktree, and contradictions in either copy are refused rather than hidden. Commands that change metadata write only the current checkout's card.

## Current lifecycle commands

All commands are `python3`, standard-library only, run from anywhere in the repository.

- `bin/work-new <epic> <slug> [--prefix P] [--title T] [--short]` — allocate the next `PREFIX-n` ID, scaffold the file set from the templates with `**Status:** backlog`, and commit only the new card folder.
- `bin/work-capture --kind bug|idea --words "<owner wording>" [--title T] [--epic E]` — create a minimal canonical backlog card with the owner's exact wording and original line endings. `--update <id>` appends evidence to an explicitly matched card; exact duplicate wording is refused unless `--force-new` is used for a new card. It never dispatches, cuts a worktree or starts a server.
- `bin/work-status <id> [backlog|in-progress|review] [--block "<reason>"|--unblock]` — display effective state, blocker, card path, exact next open step and the base state when it differs, or change nonterminal state metadata in the current checkout. It refuses `done`; only `work-finish` writes successful completion. State changes commit only `description.md`.
- `bin/work-list [--state STATE] [--kind bug|idea|task] [--epic E]` — derive the task, backlog and bug views from canonical cards. It links to the curated `work/ROADMAP.md`; it does not duplicate card descriptions.
- `bin/work-cancel <id> --reason "<reason>"` — write `cancelled.md` as an archived unsuccessful outcome, preserving the work branch, worktree and uncommitted work.
- `bin/work-plan <id>` — validate that the plan is fit to hand over. Refuses when there are no steps, no acceptance criteria, or template placeholders remain.
- `bin/work-handover <id>` — the gate to the executor. Refuses when the plan is not fit, attention is open, a blocker or terminal outcome is present, the declared estimate exceeds the ceiling, nothing is left to brief, or the card has uncommitted changes. Then cuts a worktree at `.worktrees/<id>` on branch `work/<id>`, marks the worktree card `in progress`, and hands off the executor brief.
- `bin/work-note <id> --step "<name>" --check "<command>"` — run the check and append the step with its verbatim output and exit code to `log.md`. `--message "<text>"` records a free note. The log always ends with exactly one newline, so recording a check does not itself fail `git diff --check`.
- `bin/work-commit <id> -m MSG` — commit the executor's work. `MSG` is required and must be a Conventional Commits subject (`type(scope): imperative summary`). Refuses any branch other than `work/<id>`, so executor work never lands on the base branch.
- `bin/work-resume <id>` — restart a cut-short run. Refuses when no worktree exists for `work/<id>`, or when the worktree card has a blocker, open attention or terminal outcome. Otherwise re-renders the brief with the state, exact next open step and remaining open steps.
- `bin/work-accept <id>` — run the acceptance checks in a throwaway scratch copy and report pass or fail. Requires the base branch (`WORK_BASE_BRANCH`, default `main`), clean source and target checkouts including untracked files, every step closed, a fit plan (present, non-empty, with steps and acceptance criteria, no malformed step line), attention resolved and no blocker or terminal outcome. The scratch copy is detached at the exact captured source SHA; a pre-existing scratch path is preserved, never force-deleted. Never merges.
- `bin/work-finish <id> [--approve REVISION] [-m SUBJECT]` — run the checks and publish the card as exactly ONE Conventional Commits squash commit on the base branch. The commit tree is the checked source tree plus generated `done.md`; the checkpoint history is not replayed and no separate finish commit is written. When `WORK_RELEASE_CMD` is configured, `--approve` is required and must resolve to the captured source revision; the adapter runs against that immutable revision and prepared squash, and only its success allows `done.md` and the base branch to change. A failed acceptance or release writes no `done.md` and preserves the source branch, worktree and recovery material. If release already succeeded and a later check or publish fails, `work-finish` sends the same adapter a documented `WORK_RELEASE_RECOVERY=1` request with the recovery reason; the adapter restores only the recovery point pinned to this finish's source/squash/approval/build receipt, and the refusal reports the actual main revision and whether recovery succeeded. Never claim main unchanged when another actor moved it. It applies the same preconditions as `work-accept` and verifies the source revision, target revision and target branch are unchanged before and after the release. Ignored local material retains the worktree and branch and is reported. `--reject "<reason>"` writes `rejected.md` and commits only that file; the work branch, worktree, uncommitted changes and pre-existing staged/unstaged target changes are preserved. `--force` skips only the acceptance command, never approval, release, readiness, cleanliness or preservation checks. Never pushes unless `WORK_PUSH=1`.

## The dispatch seam

Each command that hands off a prompt uses one seam. Inside a live session it prints the prompt and exits with code 97, so the session raises the agent itself. Run headless, it pipes the prompt to the command in `WORK_DISPATCH_CMD` (environment, or `bin/work.config`). That command is never hardcoded: set it to `claude -p`, an opencode invocation, or anything else. A live session is detected by `WORK_SESSION=1`, a known session marker, or a TTY; `WORK_HEADLESS=1` forces headless.

Configuration keys (environment overrides `bin/work.config`): `WORK_DISPATCH_CMD`, `WORK_ACCEPT_CMD` (default `bin/sift-accept` in this repo), `WORK_RELEASE_CMD` (this repo: `python3 bin/sift-promote`; empty for a generic project without a release step), `WORK_BASE_BRANCH` (default `main`), `WORK_ESTIMATE_CEILING` (default 25), `WORK_PUSH`. The release adapter receives `WORK_CARD_ID`, `WORK_SOURCE_SHA`, `WORK_SOURCE_TREE`, `WORK_SQUASH_SHA`, `WORK_SQUASH_TREE`, `WORK_TARGET_BRANCH`, `WORK_TARGET_SHA`, `WORK_TARGET_ROOT`, `WORK_WORKTREE` and `WORK_APPROVAL`.

## The executor's standing behaviour

Work only inside your worktree, on branch `work/<id>`, within the assigned stage. One step at a time: do the step, record its check with `work-note`, tick its box, then `work-commit`. Stop at the stage boundary and record the review/resume point even if other steps remain open. Never merge, never push, never raise sub-agents. On any stop, preserve incomplete work without marking it complete and leave a committed checkpoint so `work-resume` can pick it up. When every step in the card is closed, run `bin/work-test` once and stop; acceptance and merge are the coordinator's act. If a business question blocks you, write `question.md` and stop.

## Setup and tests

During rapid prototyping, do not create or run broad automated suites by default. Add/run only a small number of critical targeted tests for failures the owner cannot reasonably detect by looking at and using the application: silent data loss/corruption, transaction atomicity, concurrent/stale writes, incorrect profile/source versions, subtle scoring invariants and unintended model calls. Keep them within the approved task, identify the hidden failure each catches, and reuse focused existing coverage where possible. If a proposed test only repeats the implementation or checks a visible layout, label, button or ordinary interaction, use code review and actual running-app/browser acceptance instead. Do not build exhaustive permutations, new test infrastructure or coverage targets merely to look thorough. The owner's correction is specifically errors they CANNOT see in the UI, not errors they can see.

Build the affected application and inspect it in a real browser for visible behavior; HTTP200 or successful compilation is not evidence that the UI rendered. Preserved suites stay in the repository and full/broad runs require an explicit owner request. `bin/work-test` still reports SKIPPED by default; `bin/work-test --full` explicitly runs the preserved harness. `WORK_TEST_MODE=full` explicitly enables tests in `bin/sift-accept`. GitHub CI is manual-only (`workflow_dispatch`). A narrowly executed critical test is reported separately from skipped suites; never call skipped tests passed. Existing Git cleanliness, preservation and actual secret-scanning guards remain operational; they are not test-suite runs.

`bin/work-setup` wires a fresh clone: it sets `core.hooksPath` to the relative `.githooks`, makes the hooks, pre-commit steps, harness commands and leak-scanner adapters executable, and verifies the effective relative path and executable set instead of only printing success. The optional knowledge-base integration skips when no `kb/` directory exists; a missing shared tool is reported explicitly only when it applies. Test observations and the proposed smaller completion scope are in the active foundation card's `prototype-review.md`.

## Current deploy loop: production and card previews

**Staging is retired (owner, 2026-11-13).** Production is the only long-lived environment. Releases go from main straight to production through `bin/sift-promote`; cards are reviewed on a preview server built from their worktree against a fresh copy of production data. The staging server (port 8081, `data-staging`) is stopped. The staging code paths (`bin/sift-deploy --env staging`, `bin/sift-data-refresh`, `make build-staging`/`run-staging`) remain in the scripts but are not used; `data-staging/` stays on disk until the owner decides to delete it. Statements below that describe staging are kept as a record of the scripts' behaviour, not as instructions.

The deploy scripts keep production and (retired) staging isolated: separate binaries, frontend bundles, worker trees, data directories and recorded server pids. Relative destinations resolve against the **main checkout**, never a linked worktree, so artifacts built from `.worktrees/<id>` survive that worktree's removal. `bin/sift-deploy` refuses overlapping destinations.

**Environments (new defaults):**
- Production — port 8080, data `<main>/data`, binary `<main>/bin/sifty`, dist `<main>/frontend/dist`, workers `<main>/backend/workers-prod`. Updated only by `bin/sift-promote` on the owner's explicit word.
- Staging (retired 2026-11-13, not used) — port 8081, data `<main>/data-staging`, binary `<main>/bin/sifty-staging`, dist `<main>/frontend/dist-staging`, workers `<main>/backend/workers-staging`.
- State and caches — `<main>/.local/deploy` (candidates, recovery, pid files), `<main>/.local/cache/workers` and `<main>/.local/cache/frontend`.

**Live migration is explicit (historical, completed).** The then-running production (old binary on 8080, `legacy/app/dist`, shared `backend/workers`) and the live preview (8081, `data-staging`) predate this pid/path scheme. New commands refuse a busy port or a process they cannot verify; they never kill an unknown occupant or assume the old layout equals the new defaults. To migrate, stop the old environment/preview through its own owner, then run the new deploy commands once. Do not run deploy/refresh against the live defaults while the preview owns 8081 or an old server owns 8080.

**Commands:**
- `bin/sift-deploy --env staging|prod [--source REVISION] [--build-only] [--refresh-data] [--adopt-legacy]` — build a fresh candidate (Go binary, frontend bundle, worker tree with locked dependencies), back up all current artifacts, stop only the recorded server, publish atomically, start and verify `GET /api/version` plus `GET /api/health`, and restore binary, bundle, workers and a consistent SQLite database on failure. `--source` extracts the exact committed revision with `git archive` and builds that, never a dirty or moving checkout. `--adopt-legacy` is the explicit first-transition operation: it verifies the actual listening process (binary, data, `--dist`, `--workers-dir`), captures the assets it really serves for rollback, records its pid, then deploys normally; it refuses an ambiguous or unverified port owner and is refused after a completed migration. A legacy rollback restarts the captured original argv and accepts `/api/health` or `/`, because the old binary predates `--port`/`--public-port` and `/api/version`. `--recover DIR` restores a captured recovery point standalone. A normal deploy never refreshes data. Staging-only `--refresh-data` is the explicit data operation.
- `bin/sift-data-refresh [--env staging] [--from PATH] [--no-restart]` — not used since staging was retired. Explicit staging data snapshot. It stops the recorded staging server, preserves the old staging data under `.refresh-backup/<timestamp>/`, takes a consistent SQLite backup of production, copies config, config-backups, kb/evidence/answers/feedback and other root-relative data files, removes stale WAL/SHM, and fails loudly on copy/recovery errors. It refuses overlapping `--from` sources and any live preview conflict.
- `bin/sift-promote --source REVISION --approve REVISION [--adopt-legacy] [--check]` — the only command that updates production. The approval must resolve to the same pinned commit as the source; `--check` verifies and prints without deploying. It runs `bin/sift-deploy --env prod --source <sha>`. With `WORK_RELEASE_RECOVERY=1` it verifies a release receipt keyed by the finish's source, squash, approval and build, checks the current production build, restores that pinned recovery point and prints a `RECOVERY result=` receipt. Missing, stale or mismatched receipts are refused instead of rolling back another release. It is this repository's `WORK_RELEASE_CMD`, so `work-finish` invokes it with `WORK_SOURCE_SHA`/`WORK_APPROVAL`. For the first transition from the old layout, pass `--adopt-legacy` explicitly (or set it in `WORK_RELEASE_CMD` for that one release); no command silently adopts a port occupant.
- `bin/sift-preview start|status|stop|once` — continuous preview of one worktree; see below.
- `bin/sift-accept` — the acceptance command (`WORK_ACCEPT_CMD`). Defaults to builds only: `go build ./...`, `npm ci`, `npm run build` (`tsc --noEmit` + `vite build`) for app/build-touching cards; automated tests are explicitly reported SKIPPED. `WORK_TEST_MODE=full` opts into the preserved harness and Go race tests. A failed `npm ci` fails acceptance; there is no silent `npm install` fallback. The frontend build writes to a temporary directory so the scratch copy stays removable without force. Build success does not replace owner review on the card's preview.

**Preview workflow:**
1. Create a worktree for the in-progress branch: `git worktree add .worktrees/<id> work/<id>`.
2. Start continuous preview: `bin/sift-preview start --worktree .worktrees/<id> --label <id>`. It follows the worktree's frontend, backend and worker sources, including uncommitted and untracked changes, and serves it with a status banner. Always pass `--port <free port>` and `--data-dir <fresh copy of production data>`: without them the preview falls back to the retired staging port 8081 and `data-staging`. `bin/sift-preview status` reports the requested worktree/fingerprint, the generation actually served, health and build errors; `bin/sift-preview stop` stops only the recorded owner. A failed build keeps the previous healthy generation and server running. Stop the preview when its review ends: every running Sifty server runs background model work and queues on the machine-wide model lock, so a forgotten preview slows production.
3. The owner reviews the change at the preview's port. Production on 8080 is unaffected.
4. `bin/work-accept <id>` runs `bin/sift-accept` in a throwaway scratch copy after the acceptance preconditions pass. During prototyping this checks app/build-touching cards' builds and reports tests skipped; the owner reviews functionality on the preview.
5. `bin/work-finish <id> --approve <source-sha>` runs acceptance, invokes the configured release adapter against that pinned revision, and only after success publishes one squash commit (checked tree plus `done.md`) on main. A failed release leaves main, the source branch/worktree and recovery untouched.
6. The adapter is `bin/sift-promote`, which builds the pinned source and verifies production health. The first migration from the old binary/bundle layout uses the explicit `--adopt-legacy` operation; no live migration is performed by finishing a normal card.

No `work-*` command starts a preview automatically, and capturing a bug or idea never starts one. `WORK_PREVIEW_CMD` remains an unused adapter seam; the generic lifecycle commands do not embed sifty policy.

**Build-only:** `bin/sift-deploy --env <env> --build-only` builds and publishes candidates only when the target environment's port is free. It refuses to overwrite a running environment's artifacts and propagates failure. `make build` uses this path (`make build-staging` too, but staging is retired).

**Rollback:** a deploy keeps candidate/build logs and a recovery directory under `.local/deploy/<env>/recovery/`. It copies the current binary, dist and worker tree before the stop; the final SQLite snapshot is taken only after the server is verifiably stopped and before publication, so writes during shutdown are not lost. On publish, start, version or health failure it stops the candidate, restores all four and restarts the previous server for normal deploys; after an explicit data refresh it restores the pre-refresh staging data snapshot. It removes stale WAL/SHM before restoring SQLite, refuses to restore beneath a process it could not stop, does not restart an incoherent mixture when artifact/data restore is incomplete, and reports `ROLLBACK` or `ROLLBACK_INCOMPLETE` in `state.json`. One per-environment operation lock serializes deploy, build-only and refresh mutations.

**Staging data (retired):** ordinary deploys never copied production data. Use `bin/sift-data-refresh` or `bin/sift-deploy --env staging --refresh-data` deliberately. Both preserve the previous staging data tree and include root-relative candidate files such as `kb/`, not only `cv.pdf`/`profile.pdf`.

**Previews:** no preview runs by default. A running preview watches frontend/backend/worker source changes automatically; its client reloads clean pages after a new healthy generation, and edited pages show Reload instead of losing input. Use `python3 bin/sift-preview status` to see what runs. Root prompt files are in `config/prompts`; the Go package's embedded prompt copies remain under `backend/internal/prompts`. Root `app`, `sifty` and `ai` compatibility links are no longer required.
