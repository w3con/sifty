# Collection behavior specification

Status: written from the code of main `d49de9f` on 2026-11-13 by card OPS-11; not yet reviewed by the owner. The code under `backend/`, `frontend/` and `config/` is identical in main `137b7b2` (checked with a read-only diff). Production's own `search.yaml` and `runtime.yaml` and the live network were not read or exercised, so statements about what a given source returns in practice are "not verified". Requirement: R-COL in `docs/MAP.md`.

## 1. Purpose

The owner wants new vacancies from the sources they configured to appear in the Triage list without any manual work, without the application hammering any site, and without removed vacancies coming back. In `docs/MAP.md:81` the owner confirmed that there is no separate incoming stage: every collected vacancy goes straight to Triage after the filters, and collection starts when the application is opened, throttled by a cooldown. A newly stored vacancy gets the workflow status "new", which is the Triage stage (`backend/internal/store/jobs.go:496-504`, `backend/internal/store/core.go:14-23`).

Collection does three things only: it reads the listing of each enabled source, reads the detail page where the listing does not already carry the text, and stores the result as one deduplicated vacancy record per listing. It does not rank, search or assess; those run afterwards on the stored records (see section 11 and the Quick Match specification).

## 2. Sources and how they are configured

A source is one entry of `sites` in `search.yaml` in the data directory's `config/` folder (template: `config/search.yaml`): a unique `name`, an http(s) `url` and an optional `enabled` flag that defaults to true (`backend/internal/config/config.go:18-25`, `backend/internal/config/config.go:482-500`). The file is rejected on load or save when the version is not 1, there are no sites, a name is empty or duplicated, or a URL is not http(s) (`backend/internal/config/config.go:482-500`, `backend/internal/config/save.go:123-140`). The `name` is stored on every vacancy collected from that source and replaces any label the adapter used internally (`backend/internal/background/collect.go:67-68`).

The owner edits sources in Settings, Collection, Sources: list, enable or disable switch, remove, and add by name and URL (`frontend/Collection.tsx:110-136`, `frontend/Settings.tsx:25`, `frontend/Settings.tsx:53`). The server endpoints read and write `search.yaml` through the standard configuration save, which writes a timestamped backup of the previous file into `config-backups/` and refuses inline secrets, and then reloads the live configuration (`backend/internal/server/routes.go:1083-1176`, `backend/internal/config/save.go:99-120`). Adding a source requires both a name and a URL and refuses a duplicate name (`backend/internal/server/search_yaml.go:119-135`). The URL of an existing source cannot be edited in the application (`backend/internal/server/routes.go:1148-1176` toggles `enabled` only).

Which parser reads a source is decided by the host of its URL, in this order, first match wins (`backend/internal/background/collect.go:99-110`, `backend/internal/source/source.go:63-83`):
- `boards.greenhouse.io` and `job-boards.greenhouse.io`: the Greenhouse public board API for the company named by the first path segment of the URL, one request, descriptions included (`backend/internal/source/greenhouse.go:64-103`).
- `jobs.lever.co`: the Lever public postings API for that company, one request, descriptions included (`backend/internal/source/lever.go:68-108`).
- `jobs.ashbyhq.com`: the Ashby public job-board API for that company, one request, only postings marked listed, descriptions included (`backend/internal/source/ashby.go:70-117`).
- every other host: the generic source. It fetches the one listing page named by the URL and tries, in order, schema.org JobPosting data embedded as JSON-LD, then an RSS or Atom feed when the content type or the URL ends in xml, then job-looking links in the HTML, which includes the hydration data of Getro-powered boards (`backend/internal/source/generic.go:30-68`, `backend/internal/collect/parse.go:25-38`, `backend/internal/collect/parse.go:170-215`, `backend/internal/collect/parse.go:234-342`). No pagination is followed: one listing page is read per source.

The sources in the template (`config/search.yaml:9-47`) are job boards and venture-capital job pages that all use the generic path, none of them an ATS board URL. The template's comment says that a URL registers a source and that support for each site must be implemented and verified separately (`config/search.yaml:5-7`). Whether each listed source actually yields vacancies is not verified here.

Code that exists but is not connected to collection in main: a Getro adapter, a jobspy adapter that would call the jobspy worker, and an extraction-hint interface for learned per-host rules; nothing constructs them outside tests (`backend/internal/source/getro.go:20`, `backend/internal/source/jobspy.go:24`, `backend/internal/source/hint.go:12-44`). The settings `max_pages`, `max_jobs_per_source`, `max_reviewed_per_source`, `max_detail_requests`, `detail_concurrency`, `max_query_groups`, `request_timeout_ms`, `model_extraction` and the whole `network.yaml` proxy mapping are read into the configuration but not used by collection (`backend/internal/config/config.go:64-85`; no other reference in non-test code; `backend/internal/background/collect.go:22` creates the HTTP client with default options and no proxy).

## 3. What starts a collection

Four triggers exist, all ending in the same collection function and all serialised by one cross-process lock named "daily" (`backend/internal/background/trigger.go:16`, `backend/internal/store/queue.go:389-418`).

- Application open. The main page issues one unforced `POST /api/search` when it mounts, so every open or reload asks for a run and the server decides (`frontend/main.tsx:66-68`). The call is asynchronous: the server answers 202 with the run id and status "running" or "skipped" (`backend/internal/server/routes.go:401-424`). Any error, for example a lock held by a run in progress, is swallowed by the page (`frontend/main.tsx:68`).
- Cooldown. An unforced request is skipped, recording nothing, when the most recent run of either kind started less than the cooldown ago. The "most recent run" is the newest start among the on-demand run table and the daily scheduler's own table, regardless of whether that run finished or failed (`backend/internal/background/trigger.go:151-167`, `backend/internal/store/queue.go:488-502`). The cooldown is `collection_cooldown_ms` in `runtime.yaml` and defaults to 3 hours when absent; the template `config/runtime.yaml` does not list the key (`backend/internal/background/trigger.go:19`, `backend/internal/background/trigger.go:136-142`).
- Manual. The button "Collect jobs" in Settings, Collection, Sources sends `force: true`, which skips the cooldown but not the lock and not per-site pacing (`frontend/Collection.tsx:60`, `frontend/Collection.tsx:133`, `backend/internal/background/trigger.go:26`). The button is disabled while the latest run has status "running" (`frontend/Collection.tsx:133`). When the lock is held by a live process the server answers with an error that the page shows as a red banner (`backend/internal/background/trigger.go:146-149`, `backend/internal/server/server.go:118-129`).
- Per source. The API accepts a `source` value and stores it in the run row as its mode, but the collection function takes no source argument and always walks every enabled source (`backend/internal/background/trigger.go:23-24`, `backend/internal/background/trigger.go:169`, `backend/internal/background/scheduler.go:20`). The only per-source button in the code ("Search source") lives in `frontend/Sources.tsx`, a component that nothing imports (`frontend/Sources.tsx:16`; no `import` of it in `frontend/`). So per-source collection is not available to the owner.
- Daily scheduler. A goroutine checks every minute, and once at start-up, whether the configured time (`daily_hour` and `daily_minute` in `runtime.yaml`, local time zone, template 09:00) has passed today and no daily run has completed today; if so it takes the lock, records a row in its own run table, runs the collection and then the same after-collection step (`backend/internal/background/scheduler.go:59-165`, `config/runtime.yaml:14-15`). It does not look at the cooldown, and it counts only its own earlier runs as "already ran today" (`backend/internal/store/queue.go:710-730`). A run that is in progress holds the lock, so the scheduler gives up silently and tries again the next minute (`backend/internal/background/scheduler.go:134-137`).
- Disabled. When `collection_disabled` is true in `runtime.yaml`, every trigger returns "skipped" and nothing is fetched; review copies of the data use it so they never reach the internet (`backend/internal/config/config.go:83-85`, `backend/internal/background/trigger.go:52-54`, `backend/internal/background/trigger.go:125-127`, `backend/internal/background/scheduler.go:95-98`).

A run records its start, finish and a status of "complete" or "failed" in a run row; the configuration used is the snapshot taken when the run starts, and later edits apply to the next run (`backend/cmd/sifty/serve.go:96-104`, `backend/internal/background/trigger.go:169-192`). After a successful run the server recomputes Quick Match for the stored vacancies with the live configuration; a failure of that step is logged and does not fail the run (`backend/internal/background/trigger.go:184-188`, `backend/cmd/sifty/serve.go:100-102`, `backend/cmd/sifty/serve.go:156-158`).

## 4. One collection run

The run is one sequential loop with no concurrency (`backend/internal/background/collect.go:21-88`):
- It builds a fresh HTTP client and source registry, loads the active exclusion terms once, and walks the enabled sources in file order (`backend/internal/background/collect.go:22-37`).
- For each source it asks the adapter for the references to postings. An error (network failure, block, unparsable response) is logged and the whole source is skipped for this run; an empty result is silent (`backend/internal/background/collect.go:39-43`).
- For each reference it computes the canonical URL (fragment, leading "www.", tracking parameters and trailing slash removed, query sorted) and skips a URL already seen earlier in the same run, across all sources (`backend/internal/background/collect.go:46-54`, `backend/internal/collect/canonical.go:19-41`).
- It applies the exclusion terms to the title and company known from the listing, before any detail page is fetched (`backend/internal/background/collect.go:55-60`).
- It resolves the posting: the listing data is used as is when it already has title, company and description, otherwise the detail page is fetched (section 6). A failure to resolve is logged and that posting is not stored in this run (`backend/internal/background/collect.go:62-66`).
- It applies the exclusion terms again to the resolved title and company, then stores the posting (section 7). The log line at the end reports "upserted N" where N counts every posting passed to the store, including those the store silently discarded because of a deleted-listing record (`backend/internal/background/collect.go:73-86`).

The loop is implemented twice: `defaultCollect`, which runs in production, and `collectSources`, which the tests call and which additionally rescores with full-text search (`backend/internal/background/collect.go:21-88`, `backend/internal/background/collect.go:134-199`, `backend/internal/background/collect_test.go:44-114`). The tests therefore exercise the copy, not the production function.

## 5. Fetch safety and pacing

Every request of the collection layer goes through one client (`backend/internal/fetch/client.go:1-5`):
- Only http and https URLs without embedded credentials are fetched (`backend/internal/fetch/client.go:143-158`).
- Before every request, including every redirect hop, the host is resolved and the request is refused if any address is loopback, link-local, multicast, unspecified or private (10/8, 172.16/12, 192.168/16, fc00::/7) (`backend/internal/fetch/client.go:121-140`, `backend/internal/fetch/client.go:221-252`).
- Redirects are followed manually, at most six, each hop checked again (`backend/internal/fetch/client.go:109-111`, `backend/internal/fetch/client.go:163-197`).
- A response body over 8 MB is refused (`backend/internal/fetch/client.go:18`, `backend/internal/fetch/client.go:199-208`).
- The request identifies itself as "Sifty/1.0 (personal read-only job discovery)" and asks for HTML, JSON, RSS or XML (`backend/internal/fetch/client.go:174-175`).
- A 403 status or a page body that looks like a human-verification challenge ("verify you are human", Cloudflare markers, "just a moment...") is returned as a blocked result, not as content (`backend/internal/fetch/cache.go:24-38`).

Pacing applies per domain to listing pages and detail pages alike (`backend/internal/fetch/traffic.go:156-176`):
- Consecutive requests to one domain are at least 3 seconds apart plus a random jitter of up to 3 seconds (`backend/internal/fetch/traffic.go:26-27`, `backend/internal/fetch/traffic.go:106-115`).
- After a failed request the next request to that domain waits 30 seconds, doubling with each consecutive failure up to 1 hour; a success resets this (`backend/internal/fetch/traffic.go:29-31`, `backend/internal/fetch/traffic.go:94-105`, `backend/internal/fetch/traffic.go:140-144`).
- After a blocked result the domain is refused for 24 hours; later requests to it fail at once with a cooldown error (`backend/internal/fetch/traffic.go:28`, `backend/internal/fetch/traffic.go:87-91`, `backend/internal/fetch/traffic.go:135-139`).
- Responses are cached in memory, listing pages for 3 hours and detail pages for 24 hours (`backend/internal/fetch/cache.go:10-14`, `backend/internal/fetch/cache.go:83-112`).
- All of this state (pacing, backoff, block cooldown, cache) lives in the client object, and a new client is created at the start of every run, so none of it survives to the next run (`backend/internal/background/collect.go:22`). The 24-hour block cooldown therefore protects a site only within one run. This is a limit, listed in section 12.
- The forced run skips only the run-level cooldown; pacing is never skipped (`backend/internal/background/trigger.go:26`).

No overall request timeout is set: the HTTP client has no timeout and the collection passes a context without a deadline, and `request_timeout_ms` is not read (`backend/internal/fetch/client.go:106-112`, `backend/internal/background/collect.go:39`, `backend/internal/background/collect.go:62`). A server that accepts a connection and never answers could therefore hold a run open; this was derived from the code and not reproduced.

## 6. How a description is obtained and stored

A vacancy's description comes from the first of these that applies (listing-level data wins over a detail fetch):
- ATS adapters (Greenhouse, Lever, Ashby): the description in the listing API response, converted to plain text. Status "available structured description", or "missing" when empty (`backend/internal/source/greenhouse.go:94-95`, `backend/internal/source/greenhouse.go:134-139`, `backend/internal/source/lever.go:99-100`, `backend/internal/source/ashby.go:108-109`). Greenhouse and Lever use the board slug as the company name, with an initial capital for Lever; Ashby uses the organisation name from the API (`backend/internal/source/greenhouse.go:92`, `backend/internal/source/lever.go:98`, `backend/internal/source/ashby.go:92-95`).
- JSON-LD JobPosting on a listing page: the `description` field, status "available structured description" or "missing". A posting without a title or without a hiring organisation is dropped (`backend/internal/collect/parse.go:136-153`).
- RSS or Atom feed item: the longest of description, content, encoded or summary, status "feed description; may be excerpt". The company and role are split from the item title at a colon or at " at ", otherwise the company is "Unknown" (`backend/internal/collect/parse.go:182-212`).
- Getro hydration data on a listing page: the skills list only, status "skills metadata only; full description pending" (`backend/internal/collect/parse.go:332-339`).
- Plain HTML links: no description, status "pending detail fetch"; the company is read from a company element near the link, otherwise "Unknown" (`backend/internal/collect/parse.go:267-287`).
- Detail fetch, when the listing data lacks a title, company or description: the detail page is fetched through the paced client. JSON-LD on the page is used only when exactly one posting on it matches the reference by URL (tracking parameters and fragment ignored), or else by unique title and company; an ambiguous page is never guessed (`backend/internal/source/generic.go:74-99`, `backend/internal/source/match.go:15-76`). Otherwise the cleaned text of the whole page body becomes the description, status "available cleaned html", or "missing" when nothing is left (`backend/internal/source/generic.go:101-112`). A blocked detail page does not fail the posting: the listing fields are kept with status "blocked: 403" or "blocked: captcha" and no description (`backend/internal/source/generic.go:82-89`).

Text cleaning removes script, style, navigation, footer, header, noscript and svg elements, puts a line break before block elements and collapses whitespace; headings, list markers and numbering are lost (`backend/internal/collect/text.go:22-35`). The page-body fallback keeps all other text of the page, including page chrome that is not in those elements. The stored record holds only this plain text and a status string; the fetched page itself is not kept in main (see "Implemented on a branch" below).

A posting resolved without any status gets "pending detail fetch" only when its description is empty (`backend/internal/background/collect.go:69-71`, `backend/internal/background/collect.go:121-128`).

When an existing vacancy is collected again, its stored description is replaced only if the new one qualifies (section 7). The owner can also refresh one vacancy by hand with the "refresh source" action in the vacancy view (`POST /api/jobs/{id}/read`): it fetches the stored original URL again through the paced client and always overwrites the stored description and its status with the new text, even if it is shorter, then recomputes that vacancy's Quick Match (`frontend/RoleContent.tsx:48`, `backend/internal/server/routes.go:240-262`, `backend/internal/server/enrich.go:88-150`). Fetching a single URL into the catalogue is available as `POST /api/import`, which has no caller in the frontend; a failed import still creates a minimal record titled "Imported role" with company "Unknown" (`backend/internal/server/routes.go:457-475`, `backend/internal/server/enrich.go:45-84`).

## 7. Duplicates and updates

A vacancy is identified in three ways, checked together in one query when a posting is stored (`backend/internal/store/jobs.go:442-452`):
- the canonical URL of the posting equals a URL previously seen for an existing vacancy (every vacancy keeps one "sighting" row per canonical URL with the source name and last-seen time);
- its apply URL equals the apply URL of an existing vacancy;
- its identity, which is the normalised company name plus the normalised title (lower case, a few technology spellings unified, punctuation removed), equals that of an existing vacancy, provided the company is not "Unknown", the existing vacancy is not on the same host as the new posting, and the apply URLs do not conflict (`backend/internal/store/core.go:104-116`, `backend/internal/store/jobs.go:435-452`).

No match: a new vacancy is inserted with the next id, status "new", first-seen and last-seen set to now (`backend/internal/store/jobs.go:478-508`). Ids of deleted vacancies are never reused (`backend/internal/store/jobs.go:929-939`).

One match: the vacancy is updated. Several matches: the oldest id survives, and the others are merged into it, which moves drafts, revisions, sightings, snapshots, assessments, feedback and history to it, records an alias from the old id to the surviving one and deletes the duplicate rows (`backend/internal/store/jobs.go:510-545`). Workflow state is never lost on update: if any matched row was applied, the survivor is "applied"; otherwise a shortlisted row gives "saved"; otherwise a rejected row gives "rejected"; the earliest seen-at and the applied-at are carried forward (`backend/internal/store/jobs.go:547-582`, `backend/internal/store/core.go:14-23`). So a vacancy the owner dismissed stays dismissed when it is collected again.

On update the fields change as follows (`backend/internal/store/jobs.go:584-656`):
- title is overwritten with the new title; company is overwritten unless the new company is "Unknown"; last-seen is set to now;
- the apply URL is replaced when the new posting has one; expiry, location and tags are replaced when the new posting has a non-empty value;
- the description and its status are replaced together when the new description is "fresh enough" or is at least as long as the stored one and the stored one is not "ready". The code intends: a description of 100 characters or more whose status does not mention metadata, pending, missing or unavailable is fresh. In fact the code tests the status with a character-set function (`strings.ContainsAny` with the word list as one string), so any status containing any of the letters in "metadata|pending|missing|unavailable" counts as "not fresh and not ready", which includes "available structured description" and "available cleaned html" (`backend/internal/store/jobs.go:593-603`). Read from the code, not executed: the effective rule for nearly every status is that the stored description is replaced when the new one is at least as long, and a shorter new description never replaces it. The limit is listed in section 12;
- an established publication date and its basis are kept (section 8).

Each store call also writes one snapshot row holding the incoming record as JSON, every time the vacancy is collected, and refreshes the full-text index entry (`backend/internal/store/jobs.go:658-679`). The stored `source` of a sighting is not updated after the first sighting of a URL; only the seen time is (`backend/internal/store/jobs.go:628-633`).

## 8. Publication date and age

Only a genuine source publication date is stored as the vacancy's publication date. A value is accepted only when it parses as one of the supported shapes (ISO with or without a zone, date only, space-separated timestamp with zone, RFC and feed dates), is not in the future, and is normalised to UTC; a date-only value stays date-only. Anything else, including an empty value, becomes "unknown" (`backend/internal/model/date.go:8-57`, `backend/internal/store/jobs.go:383-386`). The record also stores a "basis", the name of the source field the date came from, and an empty date never carries a basis (`backend/internal/model/date.go:59-66`).

Fields accepted as publication: `datePosted` in JSON-LD, `pubDate` or Atom `published` in feeds, `first_published` in Greenhouse, `created_at` in Lever and Getro, `publishedDate` in Ashby (`backend/internal/collect/parse.go:145-151`, `backend/internal/collect/parse.go:203-211`, `backend/internal/source/greenhouse.go:97-98`, `backend/internal/source/lever.go:102-103`, `backend/internal/source/ashby.go:111-112`). Modification times (Greenhouse `updated_at`, Atom `updated`) are deliberately not taken (`backend/internal/source/greenhouse.go:49-50`, `backend/internal/collect/feed.go:40-47`).

On re-collection an established date is kept; a missing date is filled from the new posting together with its basis; a different new date never replaces the old one or lends it a basis; a missing basis is filled only when the same date is confirmed (`backend/internal/store/jobs.go:605-612`). The same rule applies to the manual refresh (`backend/internal/server/enrich.go:126-141`). Rows collected before the basis existed keep their raw dates without a basis and are shown as unverified (`backend/internal/store/migrate.go:442-451`, card COLLECTION-1 acceptance record).

What the owner sees: the list rows and the vacancy header show "Published <date> · <age>" when the basis is known, "Source date <date> · <age> (unverified)" when there is a date without a basis, and "Publication date not reported" otherwise; age is expressed in completed calendar years, months or days, or "today" (`frontend/dates.ts:45-85`, `frontend/main.tsx:155-156`, `frontend/main.tsx:165`). The "collected" date stays separate from the publication date. The Newest order has three tiers: dates with a basis newest first, dates without a basis newest first, then vacancies with no usable date, ties broken by id (`frontend/dates.ts:39-42`, `frontend/filters.ts:14`). The server keeps a copy of this key for the order of the background analysis (`backend/internal/background/newestkey.go`; the rule is in section 14.3 of the Quick Match specification). A vacancy whose expiry time (from JSON-LD `validThrough`) has passed is flagged "Listing expired" but not hidden or removed (`backend/internal/store/jobs.go:241-247`, `frontend/main.tsx:156`).

Age has no effect on any score and no vacancy is hidden or removed because of its age (card COLLECTION-1, `docs/MAP.md:79`).

## 9. Deleted-listing records

The owner can dismiss a vacancy in Triage, which only moves it to the rejected stage and keeps the record, so a later collection finds the record and leaves it rejected (section 7). Permanent Delete is a separate action, offered outside Triage and only after an explicit confirmation (`backend/internal/store/jobs.go:836-838`, `backend/internal/server/routes.go:183-205`, `frontend/DeleteRole.tsx:1-5`).

Permanent Delete refuses while a live process holds the collection or inference lock (so not during a collection run), and while the vacancy is being assessed (`backend/internal/store/jobs.go:842-854`, `backend/internal/store/jobs.go:993-1015`). Otherwise, in one transaction, it:
- writes a record for every URL the vacancy was ever seen under (original URL, apply URL, and all sightings of the vacancy and of every vacancy merged into it), as the SHA-256 hash of "url:" plus the canonical URL, into the deleted-listings table (`backend/internal/store/jobs.go:862-915`, `backend/internal/store/core.go:118-132`, `backend/internal/store/migrate.go:202`);
- deletes the vacancy and all its related rows and aliases, removes it from the full-text index and from the discovery cache, and advances the id sequence so the id is never reused (`backend/internal/store/jobs.go:917-988`).

At collection, a posting whose original URL or apply URL hashes to a recorded value is dropped silently by the store, and the store call reports success with id 0 (`backend/internal/store/jobs.go:422-433`). The check is by URL only: the same role under a different URL, not matching by identity, comes back as a new vacancy. The check happens after the detail page has been fetched, not before, and the run's counter still counts the posting (`backend/internal/background/collect.go:62-82`). The store has a restore path that clears these records for a URL, but no code outside tests calls it, so the owner cannot undo a permanent deletion from the application (`backend/internal/store/jobs.go:416-421`; no non-test caller of `Upsert` with restore true).

## 10. Filters and exclusions applied at collection

Only one filter runs at collection: the exclusion terms the owner manages in Settings, Collection, Search, "None of these" (stored in the stop-words table, not in `search.yaml`) (`backend/internal/background/collect.go:30`, `backend/internal/store/stopwords.go:13-38`, `frontend/Collection.tsx:152-158`). A term is trimmed and lower-cased and matches as a literal substring of the title or of the company name, case-insensitively; a posting whose title and company are both empty never matches (`backend/internal/store/stopwords.go:20-22`, `backend/internal/store/stopwords.go:87-108`, `backend/internal/background/collect.go:214-220`). A matching posting is not stored at all, and it is skipped before its detail page is fetched when the title came from the listing (`backend/internal/background/collect.go:55-60`, `backend/internal/background/collect.go:73-76`). Roles already stored are hidden by the same terms at read time, derived on every read, so removing a term brings them back and the next collection stores postings again (`backend/internal/store/jobs.go:287-291`). The interface shows how many stored roles a new term would hide before it is added (`backend/internal/store/stopwords.go:140-166`, `frontend/Collection.tsx:57-58`). If the terms cannot be read, collection proceeds unfiltered and logs it (`backend/internal/background/collect.go:201-210`).

Not applied at collection: the search expressions ("Any of these" and "All of these") and the block rules by company or source. Every posting that is not excluded is stored. Search expressions only affect search and ranking of stored vacancies (`backend/internal/profile/ranking.go:204-225`, `backend/internal/server/routes.go:1031-1080`), and block rules hide stored vacancies at read time (`backend/internal/store/jobs.go:281-284`). Details of search and ranking belong to the search specification.

## 11. What the owner sees

- Whether a run is going: the "Sifty" mark in the header animates while the latest run has status "running" (polled every 2 seconds while running, 5 seconds otherwise, only while the tab is visible), and Settings, Collection, Sources shows "Collection in progress…" and disables "Collect jobs" (`frontend/Brand.tsx:14-19`, `frontend/Collection.tsx:34`, `frontend/Collection.tsx:114`, `frontend/Collection.tsx:133`).
- What the API reports for the latest run: id, start, finish, status, mode and, for on-demand runs, per-source rows and events read from two tables; for daily runs these are always empty lists (`backend/internal/server/routes.go:426-433`, `backend/internal/store/queue.go:488-570`). Nothing in main writes the per-source and event rows, so the lists are always empty, and nothing in main writes the per-source health table either (`backend/internal/store/queue.go:521-562`; only tests call `Store.Health`, `backend/internal/store/jobs.go:1050`). The progress component that would render them, with counts of reviewed, added, updated and duplicate postings per source, is in `frontend/Sources.tsx`, which is not mounted anywhere (`frontend/Sources.tsx:4-19`).
- Result of pressing "Collect jobs": the notice "Collection started." appears whenever the server accepted the call, including when the server answered "skipped" because collection is disabled (`frontend/Collection.tsx:60`, `backend/internal/background/trigger.go:125-127`). Errors the server raises show as a red banner.
- Errors: a failed source, a failed detail fetch, a rejected store call and a failed Quick Match recompute are written to the server log only; nothing about them reaches the page (`backend/internal/background/collect.go:39-43`, `backend/internal/background/collect.go:62-66`, `backend/internal/background/collect.go:78-81`, `backend/internal/background/trigger.go:184-188`). A run whose function returns an error is marked "failed"; the only error the function returns is a failure to build the HTTP client, which cannot happen with default options (`backend/internal/background/collect.go:22-25`, `backend/internal/background/trigger.go:178-183`). In practice a run ends "complete" even when every source failed. This was derived from the code, not reproduced.
- A source that returns no vacancies shows nothing at all: no event, no status, no warning (`backend/internal/background/collect.go:39-45`).
- New vacancies appear in Triage with status "new" as the catalogue reloads; their Quick Match results are computed immediately after the run for the stored vacancies, locally and without a model call (`backend/internal/background/trigger.go:184-188`, Quick Match specification section 14).

## 12. Known limits and defects

Each item with its card or "no card".

- Per-source runs, events and health are never written, so the run detail is empty (card COL-4, founded, not scheduled).
- The per-source progress component and the per-source "Search source" button are not reachable in the interface, and the per-source request is ignored by the server (no card; COL-4 assumes the component is mounted).
- The manual button reports "Collection started." even when the run was skipped (no card).
- The Search page says that changes "apply to the next collection" and `search.yaml` says the terms "guide discovery", but collection does not read the search expressions (no card).
- `search.yaml` says the application must flag unsupported sources; a source that yields nothing, or fails, is silent in the interface (no card).
- The numeric collection limits and `request_timeout_ms` in `runtime.yaml` and the proxy mapping in `network.yaml` have no effect on collection; there is no overall request timeout (no card).
- The 24-hour block cooldown, failure backoff and page cache are lost at the end of every run because a new client is created per run; a site that blocked the previous run is requested again at the next one (no card).
- Listings with a deleted-listing record are still fetched before being discarded, and they are counted as stored in the log (no card).
- The description replacement rule uses a character-set test where a word-list test was intended, so the "fresh" and "ready" checks do not work as written (no card).
- Every collection of a vacancy adds one snapshot row; growth over time was not measured (no card).
- Permanent deletion cannot be undone from the application, although a restore path exists in the store (no card).
- A collection run left "running" by a process that was killed stays "running": no start-up step marks it interrupted, the header keeps animating and "Collect jobs" stays disabled until a newer run exists, which an application open can start once the cooldown has passed; the lock itself is reclaimed from a dead process (`backend/internal/store/queue.go:400-406`; no card; derived from the code, not reproduced).
- A manual or application-open run does not count as "already ran today" for the daily scheduler, so the scheduler can start a second full collection after the first one on the first open after the daily time (`backend/internal/store/queue.go:710-730`; no card; derived from the code, not reproduced).
- The Greenhouse and Lever adapters use the board slug as the company name (no card).
- The generic source reads one listing page per source and uses the whole cleaned page body as the description when no structured data exists, so page chrome can end up in the description (no card for main; card INBOX-2 changes this for We Work Remotely and Web3 Careers on its branch).
- Category pages stored as vacancies: Remotive (72 or 73 rows, see Contradictions), Remote3 (40 rows) and foreign salary blocks in 195 We Work Remotely texts (cards COLLECTION-2 and INBOX-2).
- The store's code comment that collection no longer enqueues assessments is right for collection, but the assessment worker calls `EnqueueAll` every 30 seconds, and the comment on `defaultCollect` still says it "enqueues them for assessment"; belongs to the assessment specification (`backend/internal/store/jobs.go:815`, `backend/internal/background/assessment.go:126`, `backend/internal/background/collect.go:17-20`).
- Adding a source with an empty URL fails on the server although the form labels the field "URL (optional)" (`frontend/Collection.tsx:129`, `backend/internal/server/search_yaml.go:123-124`; no card).
- Not verified: per-source yield of any listed source against the live network; what `GET /api/health` returns when the health table is empty; the values in production's own `search.yaml` and `runtime.yaml`; behaviour of hand edits to the configuration files without a UI save.
